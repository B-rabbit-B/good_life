# 步骤 06：SDK 打包与 MCP 封装

## 目标

把步骤 02 至 05 的领域能力，整理成一份边界清晰、可独立使用的 Python SDK，再在其上包一层 MCP 服务，让任何支持 MCP 的智能体都能调用。这是作品集里最能体现架构能力的一步，也是第一阶段的收官。

## 范围

- SDK 边界梳理：明确哪些能力对外开放、哪些是内部实现，对外的输入输出格式统一、稳定、有版本号。
- 能力清单归类：
  - 经期：记录、查询统计、查询预测、查询某日阶段、查询阶段提示。
  - 医嘱：录入待确认条目、确认与修改、查询当前约束、查询待复核项、提出解除建议、确认解除。
  - 营养与饮食：检索食物、记录一餐、查询每日汇总、评估候选食物或餐食。
  - 健身：检索动作、记录训练、查询汇总、查询今日训练信号。
- 用户上下文传递方式：每次调用都必须明确"代表哪个用户"，SDK 内部据此做隔离，不允许跨用户。
- 权限分级：读取类能力与写入类能力分开授权；医嘱确认与解除这类关键动作，必须携带"来自用户确认"的凭证，智能体不能替用户确认。
- 错误与降级约定：数据不足、无权限、未找到、需要人工确认等情况，返回统一、可被智能体理解的结构化说明。
- MCP 服务：把上述能力以工具的形式暴露，每个工具配有面向模型的清晰说明、参数说明与使用限制。
- 对使用者的说明文档：SDK 使用说明、MCP 工具说明，均用自然语言，配示意性场景，不放代码。

## 明确不做

- 智能体与大模型逻辑，放到步骤 08。
- 面向第三方开发者的开放平台、计费与密钥管理。
- 新增领域功能，本步骤只封装已有能力。

## 依赖

步骤 02、03、04、05。

## 关键设计

- 分层：领域服务在下，SDK 是稳定的外壳，MCP 是 SDK 的薄薄一层适配，MCP 里不写业务规则。
- 安全关键点：写入类工具默认需要显式授权；医嘱确认、解除这类动作不作为模型可直接调用的工具，而是由前端用户操作触发，模型只能"提出建议"。
- 工具粒度：一个工具只做一件事，说明里写清楚"什么时候该用、什么时候不该用"，降低模型误用概率。
- 版本管理：SDK 的对外能力带版本，变更遵循向后兼容原则。
- 可观测性：每次工具调用都记录调用者、用户、工具、结果概况，便于审计与调试，敏感内容不写入日志。

## 交付物

- SDK 能力清单文档，含每项能力的用途、输入含义、输出含义、失败情形。
- MCP 工具清单文档，含每个工具的面向模型说明与授权级别。
- 权限与授权设计说明，特别是医嘱确认、解除的处理方式。
- 使用说明文档：如何在本地启动 MCP、如何在支持 MCP 的客户端里接入。
- 调用审计说明。

## 验收标准

1. 不经过任何自家前端，只用一个通用的支持 MCP 的客户端，就能完成：记录经期、查询预测、录入医嘱待确认、记录一餐、评估食物、记录训练。
2. 在该客户端里，无法通过工具直接确认或解除医嘱，只能提出建议。
3. 调用时没有指明用户，或指向了他人，会被拒绝。
4. 读取类与写入类的授权分开生效，仅有读取授权时，写入被拒绝。
5. 每个工具的失败情形返回统一的结构化说明，客户端能给出可读的提示。
6. 每次调用都能在审计记录里查到，且审计中不含医嘱正文等敏感内容。
7. SDK 使用说明与 MCP 工具说明齐全，别人按文档能独立接入。

## 开源参考与许可证注意

- 可参考已有的营养类、健康类 MCP 服务的工具设计思路，如营养记录、营养库检索类项目，仅借鉴设计，不直接复用。
- 引入 MCP 相关依赖前确认许可证。

## 风险与对策

- 风险：模型误调用写入类工具造成脏数据。对策：写入类工具最小化、说明写清楚、关键动作不暴露给模型。
- 风险：SDK 边界划得不稳，后续频繁破坏兼容。对策：先冻结能力清单再封装，变更走版本。
- 风险：MCP 生态变化较快。对策：MCP 层保持极薄，随时可替换。
