# 适配层选型说明

## 一、结论

步骤文档原本的设计是采用开源库 LiteLLM 作为统一适配层。实际实现时没有采用，而是自己写了三个适配器：兼容格式（openai_compatible）、Claude（anthropic）、Gemini（gemini）。这个取舍是在用户确认后做出的，理由如下。

## 二、为什么不用 LiteLLM

1. 供应链风险。调研得到的信息是：2026 年 3 月 24 日，LiteLLM 在 PyPI（Python 的公共软件包仓库）上发布的 1.82.7 与 1.82.8 两个版本被投毒，带有窃取凭证的恶意代码，会读取运行环境里的密钥。这条信息来自调研，本项目没有自行复现，请读者以官方的安全通报为准再次核对。无论细节如何，它说明了一个事实：适配层这类库会在进程里直接接触用户的模型密钥，本项目又同时持有字段加密密钥和登录签名密钥，一旦适配层依赖出事，影响面是全部用户的全部密钥。本项目是健康类应用，宁可少依赖。
2. 依赖很重。LiteLLM 是一个覆盖上百家服务的大库，会带来大量间接依赖，每多一个依赖就多一份被投毒、被弃维护、版本冲突的风险；而本项目只需要其中很小的一部分。
3. 需求很窄。本步骤只需要三件事：拉取模型列表、发一次对话（含图片与工具定义）、把各家的错误归成用户看得懂的几类。这些用标准的 HTTP 请求就能完成，自写的三个适配器连同共用部分合计约 600 行（含注释）。
4. 能力判断要自己掌控。本项目要的是“支持、不支持、未知”三种状态，允许用户手动覆盖，并且对看图这类关键用途做“未知也拒绝”的保守处理；错误说明也要是带下一步建议的中文。这些规则与具体的业务绑得很紧，放在自己的对照表里最容易讲清楚、也最容易改。

说明：LiteLLM 是 MIT 许可，从许可证角度可以嵌入使用，没有采用的原因是上面几条，不是许可证。

## 三、自写适配器的范围

已做：

- 拉取模型列表（Claude 与 Gemini 支持分页，最多 10 页），结果去重并按编号排序。
- 非流式的单轮请求：系统消息、用户消息、助手消息。
- 图片：以 base64 内嵌在用户消息里，转换成各家的图片写法。
- 工具：把统一的工具定义转换成各家的写法，并把模型返回的工具调用解析成统一的名称、参数、调用编号。
- 用量：输入与输出的 token 数。
- 错误归类：九类统一的错误，每家按自己的错误格式补充规则（见《服务类型与调用方式》）。
- 安全约束：密钥只放请求头、发请求前检查密钥格式、不跟随重定向、错误文字去掉密钥后再使用。

没做（也不在本步骤范围内）：

- 流式输出（边生成边返回）。
- 工具调用结果回传给模型的多轮往返：适配器能解析模型发出的工具调用，但统一的消息类型里还没有“工具结果”这一种，留给步骤 08 的智能体层按需要扩展。
- 向量、语音、绘图、视频等非对话类接口。
- 自动重试、模型降级与备用切换、计费与用量统计（步骤文档的“后续再议”）。

## 四、以后如何扩展

- 新增一个兼容格式的服务：不需要写任何代码，在设置里填上地址与密钥即可（预设只是帮忙填默认地址）。
- 新增一种格式特殊的服务：在适配器目录里新增一个文件，沿用共用的请求与错误处理基类，实现“拉取模型”和“对话”两个方法，必要时补充这家特有的错误归类；然后在适配器工厂与服务类型清单里登记，补上自动化测试与文档。
- 新增或修正模型的能力：编辑能力对照表这一个数据文件，新增规则时注意把更具体的规则放在前面；用户也可以随时在模型上手动标注，不必等待发布。
- 如果将来某个服务的格式与现有三种差别很大，也可以只为它新增一个适配器，不影响其他服务。

## 五、参考了哪些思路

- 按厂商分策略：参考 Cherry Studio 的设计思路，不同厂商的拉取与解析各用一套策略，而不是硬把所有服务塞进同一种格式。只借鉴思路，没有拷贝任何代码（Cherry Studio 与 LobeHub 的许可证有限制或有传染性）。
- 设置页的交互：参考 LobeHub 的模型列表页的交互思路（添加服务、获取模型、逐个模型标注能力），将在前端步骤中落实。只借鉴交互思路，不拷贝代码。
- LiteLLM：了解过它拉取模型列表与判断能力的思路，没有引入这个库。

## 六、代价与风险

- 自己维护三个适配器，厂商接口变化时需要跟进；对照表也需要持续补充。
- 适配器写的是公开文档里的格式，真实服务的细节可能不同。为此提供了实测脚本，让用户用自己的密钥逐家核对；目前 Claude 与 Gemini 只做了模拟测试，没有实测，见《实测记录》。
- 本步骤没有新增任何依赖，HTTP 请求使用项目已有的 httpx2。
