# 步骤 01 数据表说明

本文说明步骤 01 建立的四张数据表。表结构由数据库迁移脚本统一管理，按顺序执行即可在空库中建出全部表。

阅读约定：

- “是否必填”指数据库层面该列能否为空。
- “是否加密”指该列存入数据库时是否已被加密，加密后在数据库里只能看到密文，需要持有加密密钥才能还原。
- 所有时间列都带时区。

## 一、users（用户账号）

存放登录账号信息，是其他表的归属根。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 用户唯一标识 | 是（主键） | 否 | 随机生成的唯一编号（UUID） |
| username | 登录用户名 | 是 | 否 | 3 到 32 位，只能是字母、数字、下划线；统一存小写，因此不区分大小写；全表唯一 |
| password_hash | 密码的加盐哈希 | 是 | 不适用（只存单向哈希，不存明文） | 使用 argon2id 算法生成，无法反推出原密码 |
| token_version | 登录令牌版本号 | 是 | 否 | 初始为 0；每次退出登录加 1，加 1 后该用户此前签发的所有令牌立即失效 |
| created_at | 注册时间 | 是 | 否 | 注册时由数据库自动填写 |

## 二、disclaimer_acceptances（免责声明确认记录）

记录每个用户确认过哪个版本的免责声明，以及何时确认。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 记录唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id；用户被删除时，其确认记录一并删除 |
| version | 确认的免责声明版本 | 是 | 否 | 版本号是日期形式的字符串，当前版本为 2026-09-30 |
| accepted_at | 确认时间 | 是 | 否 | 确认时由数据库自动填写 |

补充说明：

- 同一个用户对同一个版本只会有一条记录（数据库设有唯一约束），重复确认不会产生重复行。
- 免责声明升级到新版本后，旧版本的记录仍保留，但用户需要重新确认新版本才能继续使用业务接口。

## 三、profiles（个人档案）

每个用户一份档案，第一次读取档案时自动创建空档案。档案与账号分表存放，可以随时修改。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| user_id | 归属用户，同时是主键 | 是 | 否 | 指向 users 的 id，一个用户只能有一份档案；用户被删除时档案一并删除 |
| gender | 性别 | 否 | 否 | female（女）、male（男）、other（其他）三选一 |
| birth_year | 出生年份 | 否 | 否 | 整数，不早于 1900 年，不晚于今年 |
| height_cm | 身高（厘米） | 否 | 是 | 数值，范围 50 到 250 |
| weight_kg | 体重（千克） | 否 | 是 | 数值，范围 20 到 300 |
| activity_level | 活动水平 | 否 | 否 | sedentary（久坐）、light（轻度）、moderate（中度）、active（活跃）、very_active（非常活跃）五选一 |
| goal | 目标 | 否 | 否 | lose_fat（减脂）、gain_muscle（增肌）、maintain（维持）、none（无特殊）四选一 |
| diet_preferences | 饮食偏好 | 是 | 否 | 文字标签列表，最多 30 个，每个 1 到 32 个字符；默认是空列表 |
| food_avoidances | 忌口 | 是 | 否 | 文字标签列表，规则同饮食偏好；默认是空列表 |
| health_conditions | 慢性病或特殊情况（自填） | 否 | 是 | 自由文本，最长 1000 个字符 |
| notes | 备注 | 否 | 是 | 自由文本，最长 1000 个字符 |
| cycle_tracking_opt_out | 是否主动关闭经期功能 | 是 | 否 | 是或否，默认否；女性用户选“是”后，经期模块对其不开放 |
| updated_at | 最近修改时间 | 是 | 否 | 创建时取数据库当前时间；之后每次通过服务修改档案时，由服务在写入时一并更新。数据库本身不会自动更新它，绕过服务直接改库不会改变这一列 |

补充说明：

- 身高、体重、健康状况、备注属于敏感字段，全部加密后存储。
- 修改档案时，把某个字段显式设为“空”表示清除该字段；饮食偏好、忌口、是否关闭经期功能这三项清除后回到各自的默认值（空列表、否）。
- 性别和“是否关闭经期功能”会被集中折算成“哪些模块对该用户开放”，后续步骤只从这一处判断，不各自重复写规则。

## 四、profile_changes（档案修改记录）

每次档案发生实际变化，就追加一条记录，只增不改。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 记录唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id；用户被删除时记录一并删除 |
| changed_at | 修改时间 | 是 | 否 | 由服务在写入时填写 |
| changes | 本次修改的内容 | 是 | 是 | 整体加密。解密后是“字段名对应旧值与新值”的结构，一次修改多个字段就有多项 |
| seq | 自增序号 | 是 | 否 | 由数据库自动递增生成，不能手工填写，也不对外返回；用于同一时刻多条记录的稳定排序 |

补充说明：

- 只有值真正发生变化的字段才会被记录；提交与现有值完全相同的内容，不产生修改记录。
- 修改记录里含有旧值和新值，可能包含敏感信息，所以整条内容都加密，而不是只加密个别字段。
- 读取修改记录时按时间倒序返回，修改时间相同的按自增序号倒序（后写入的在前），一次最多返回最近 50 条。

## 五、归属约定

- 除 users 以外，每张表都有用户归属列（user_id），指明这行数据属于哪个用户。
- 所有业务数据的查询都统一从同一个入口发起，这个入口固定加上“只查当前用户”的条件，各处代码不再自己重复判断。
- 任何接口都不接受客户端传入的用户编号，当前用户只从登录令牌里取得，因此用户无法通过改请求参数去读写别人的数据。
- 有一项自动化检查负责把关：它会遍历数据库中所有已登记的表，除 users 外只要有哪张表缺少用户归属列，测试就会失败。所以后续步骤新增的表也必须遵守这条约定，否则无法通过测试。
