# 备份与恢复预案

本文说明这个项目的数据怎样备份、怎样恢复、恢复后怎样核对，以及用户删除账号后备份应当怎样处理。本文只写做法与原则，不含命令；具体命令见 README 第 26 节“备份与恢复”。

## 一、备份什么，不备份什么

要备份的有两样，缺一不可：

1. 数据库。全部用户数据都在数据库里：账号、档案、经期、医嘱（含医嘱原件与照片这类文件内容，它们存在数据库里而不是磁盘上）、饮食、健身、对话、偏好、模型服务设置、授权与调用审计、单独同意记录。健康相关的字段在库里已经是加密后的内容。
2. 字段加密密钥，也就是配置里的 FIELD_ENCRYPTION_KEY。数据库备份里的加密字段只有配上这把密钥才能读出来，它不在数据库里，必须单独备份。

不备份的东西：

- 登录签名密钥 JWT_SECRET：丢了只是所有人要重新登录，重新生成即可，不值得备份。
- 前端的打包产物、依赖目录、测试库 goodlife_test 与端到端测试的截图与轨迹：都可以由源码重新生成，或本来就是临时的。
- 用户在红队脚本、实测脚本里用的真实模型密钥文件：它们是用户个人的密钥，按各自服务的方式保管，不放进项目备份。
- 本机以外的任何第三方服务里的数据（模型服务、高德）：它们不属于本项目。

## 二、多久备份一次，存在哪里

- 频率：数据库每天备份一次；每次大版本迁移之前，以及准备删除或批量处理数据之前，额外手动备份一次。密钥只在第一次生成时与每次更换时备份，平时不变。
- 保留：每天的备份保留最近 30 天；每个月的第一份再多保留一年，然后删除。到期删除是备份管理的一部分，不是可选项（原因见第六节）。
- 存放：数据库备份放在仓库之外、用户自己控制的加密存储里，至少两处，其中一处不在运行服务的这台电脑上。绝不放进代码仓库，也不放进任何会同步到公开位置的目录。
- 密钥备份与数据库备份分开存放：放在密码管理器或离线介质里。两者放在一起，拿到备份的人就能解出全部健康数据；两者都丢，数据就彻底没了。

## 三、谁能访问

- 数据库备份与密钥只有项目所有者本人能访问，没有其他人、也没有任何自动化流程需要读取它们。
- 持续集成使用的是临时的全新测试库，里面没有真实用户数据，不使用本文说的备份与密钥。
- 备份里包含用户的加密后的健康数据，按个人敏感信息对待：不通过聊天工具、邮件或截图传递，不发给协助开发的任何人或工具。

## 四、恢复的步骤

恢复分两种场景，步骤的顺序相同：

1. 先停下服务，确认要恢复的是哪一份备份、恢复到哪一个库。恢复会覆盖目标库里同名的内容，所以不要对正在使用且没有备份的库直接恢复；先给现有库做一次备份再继续。
2. 准备好数据库服务（全新的或原来的），把备份导入。
3. 把当初备份下来的字段加密密钥放回配置。密钥必须与做备份时的那一把完全一致。
4. 把数据库结构迁移到当前版本。如果备份来自更旧的版本，迁移会把它升到最新；备份来自更新的版本时，不要用旧代码恢复。
5. 启动服务，进入核对。

具体命令见 README 第 26 节。

## 五、恢复后怎样核对

- 迁移版本：确认数据库的迁移版本与代码一致，没有停在旧版本上。
- 数量：对比用户数与备份时记录的数量是否一致；有条件时再抽几张主要表看行数。
- 能解密：用一个已有账号登录，打开档案、医嘱、对话与饮食记录，内容能正常显示。如果有的页面报内部错误或内容为空，首先怀疑密钥不对。
- 文件内容：打开一份医嘱原件与一张保留的照片，确认能下载并显示。
- 登录与授权：已有账号能用原来的密码登录；如果登录签名密钥也被换过，所有人重新登录属于正常现象。
- 删除过的账号：对照第六节的记录，把恢复带回来的、用户已要求删除的账号再删一次。

核对通过后再对外恢复服务，并把这次恢复的日期、使用的备份与核对结果记下来。

## 六、删除账号与备份的关系

用户在界面里删除账号，立即彻底删除线上数据库里该用户的全部数据，不做冻结，也不可恢复。但这个操作不会也不能改动已经做好的备份：

- 残留：删除之前做的备份里仍然有该用户加密后的数据，直到那份备份按第二节的保留期被删除。因此，用户删除账号后，最迟在保留期（最近 30 天的每日备份）结束时，这个用户的数据才会从每日备份里完全消失；如果它还出现在被多保留一年的月度备份里，则要等那一份到期。
- 过期删除：到期的备份必须真的删掉，而不是无限期留着。备份的保留期要如实告知用户，隐私说明里写的就是这个口径。
- 恢复带回删除账号：恢复一份旧备份会把此后已删除的账号一并带回来。恢复之后，要对照删除请求的记录，把这些账号再删一次，然后才对外恢复服务。所以每次用户删除账号，都要记下账号与删除日期，用于这项核对。
- 没有密钥就无法读取：即使残留的备份被他人拿到，没有字段加密密钥也读不出健康相关的字段，这是密钥与备份分开存放的另一个原因。

## 七、字段加密密钥丢失的后果

- 数据库里已经加密的字段（档案中的身高体重健康状况与备注，经期与医嘱的内容，医嘱原件与文件名，饮食与训练备注，模型服务的密钥，智能体的对话、偏好与开场问题，拍照识别结果与照片，餐厅的大致区域）永远无法解出，没有任何补救办法，包括备份也一样。
- 账号本身、登录与不加密的结构化数据仍然可用，但对应模块的数据读不出来，相关界面会报内部错误。
- 唯一的出路是请用户重新录入，或者清空这些模块的数据重新开始。所以密钥备份与数据库备份同等重要，更换密钥前要先把旧密钥与旧数据一起备份；更换密钥本身会让已有的加密数据读不出来，只有在明确打算清空数据时才做。
