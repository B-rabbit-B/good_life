# 依赖故障预案

本系统运行时依赖三项外部或独立的东西：数据库、模型服务（用户自己配置的第三方）、高德（附近餐厅用，服务端配置）。本文逐项写它们不可用时系统的表现（错误码与界面）、用户所见、恢复方法与恢复后要核对什么。本文不含命令，需要命令的地方指向 README 的对应章节。

共同原则：界面只原样显示后端给的错误说明与错误码，不替后端判断业务；任何日志只记方法、路由模板、状态码、错误码与异常类名，不记请求内容、响应内容与异常文字，所以排查故障时看错误码与异常类名，不要指望日志里有用户的内容。

## 一、数据库不可用

### 系统表现

- 后端处理任何要读写数据库的请求时，数据库连接抛出连接类错误。未处理的异常由统一的请求日志中间件接住，返回状态码 500、错误码 internal_error、说明“服务器内部错误”；日志里只有方法、路由模板、状态码与异常类名。
- 不要读数据库的接口（例如健康检查）仍然正常返回，所以健康检查正常不代表数据库可用。
- 本机的智能体服务（MCP）读不到数据库时，工具调用返回内部错误，错误码同样是 internal_error。
- 所有用户的所有业务页面同时受影响；没有任何数据被改写，因为写入没有发生。

### 用户所见

- 登录、读档案、聊天、记录饮食或训练等操作都会失败，界面显示后端给的“服务器内部错误”与错误码 internal_error，并提供重试。网络本身不通时是另一回事：界面显示“网络连接失败，请检查网络后重试”，错误码 network_error，那是浏览器连不上后端，不是数据库的问题。
- 已经打开的页面里已加载的内容仍然可见，但再提交的操作会失败；界面不会假装成功。

### 恢复方法

1. 先确认是数据库不可用而不是后端不可用：后端进程在，请求却返回 internal_error，通常就是数据库。
2. 查看数据库服务是否在运行、磁盘是否已满、连接数是否耗尽、配置里的数据库地址与端口是否还对（本机端口被占用时要同时改两处，见 README 第 9 节）。
3. 启动或修复数据库服务（本机用数据库容器，命令见 README 第 2 节）；数据库容器重建后数据卷还在则数据还在。
4. 数据损坏或数据卷丢失时，按《备份与恢复预案》恢复，命令见 README 第 26 节。

### 恢复后核对

- 健康检查之外，再用一个已有账号登录，打开档案与对话，确认读写正常。
- 迁移版本与代码一致；故障期间失败的写入没有留下半截数据（失败的请求整个事务回滚）。
- 用户故障期间没提交成功的内容需要重新提交，界面没有做离线草稿的承诺。

## 二、模型服务不可用

模型服务是用户在“模型配置”里填的第三方服务，不由本系统运行，可能因为密钥错误、额度用完、限速、超时、服务商故障或地址写错而不可用。

### 系统表现

- 智能体聊天：配置类问题（没选对话模型、模型不支持工具调用、密钥或地址需要改）原样返回，没选对话模型时是状态码 409、错误码 agent_model_not_configured；其余调用失败统一转成状态码 502、错误码 agent_model_error，说明以“模型调用失败”开头，后面跟模型服务那边的原因说明。流式聊天时，错误以单独一个错误事件交出，流里不会有已推送的回答片段（回答只在输出检查通过后才开始推送）。
- 模型配置页的测试与拉取模型：返回各自的错误码并带中文说明与下一步建议，例如密钥无效、地址不通、模型不可用、额度用完、被限速、超时、服务商出错。
- 拍照识别：需要“看图识别”用途的模型；模型不可用时识别失败并给出原因，可以重试或改用手动录入，不会写入饮食记录。
- 规则、数据与引擎不依赖模型：医嘱约束、饮食判断、经期与训练的读写都照常工作；输出检查也不依赖模型，所以模型出错时不会产生违反医嘱的回答，只是没有回答。

### 用户所见

- 聊天里出现一条错误提示，显示错误码 agent_model_error 与原因说明，可以重试；没选模型时提示去模型配置选择对话模型。
- 拍照识别页显示识别失败与原因，提供重试与手动录入。
- 其余页面不受影响。

### 恢复方法

1. 先看错误说明里的原因：密钥问题就到服务商的控制台核对密钥、重新填写；额度用完就充值或换服务；被限速就稍等；超时或服务商出错通常是对方的临时问题，稍后再试或换一个模型。
2. 在模型配置页对该服务做一次测试，结论会区分密钥、地址与模型三类问题并给出下一步。
3. 用户可以配置多个服务并把用途切换到另一个服务的模型。
4. 本系统没有把用户的聊天内容转给任何别的服务来“兜底”，也不自动切换模型。

### 恢复后核对

- 再发一轮聊天，确认能正常回答，回答里仍附医嘱提醒与依据，且没有出现医嘱禁忌的食物。
- 拍照识别再试一张照片，确认能给出菜品与营养，匹配不上的仍标为待确认。
- 模型配置页里密钥仍只显示掩码。

## 三、高德不可用

高德只用于附近餐厅推荐，密钥由服务端配置，用户不需要也看不到它。

### 系统表现

- 服务端没有配置高德密钥：附近餐厅功能关闭，相关接口返回状态码 503、错误码 restaurant_not_configured，说明提示联系管理员在服务端配置；其他功能不受影响。
- 配置了密钥但高德出错、超时或无法连接：返回状态码 502、错误码 restaurant_service_failed，说明“附近餐厅服务暂时不可用，请稍后再试”。定位与地址解析环节也走同一个错误。
- 智能体按地点调用附近餐厅工具时，工具把错误以结构化结果交回模型，由模型据此告知用户；系统不会凭空生成餐厅数据。
- 精确位置从不入库，所以高德故障不会留下位置数据。

### 用户所见

- 餐厅页显示后端给的错误说明与错误码，提供重试；功能关闭时显示功能未开启的说明。
- 聊天里问附近吃什么时，工具把错误以结构化结果交回模型，由模型据此告知用户；系统不会凭空生成餐厅数据。

### 恢复方法

1. 密钥问题：到高德开放平台核对密钥类型必须是“Web 服务”、是否被停用、是否超出调用额度，修正后写回服务端配置并重启后端（配置见 README 第 4 节与第 20 节）。
2. 服务出错或超时：属于对方的临时问题，稍后再试；服务端所在网络如果能访问外网才能访问高德。
3. 暂时不需要这个功能时，把密钥留空即可关闭，不影响其他功能。

### 恢复后核对

- 用手动输入的地点做一次搜索，确认返回餐厅并带导航链接，且按医嘱忌口给出每类餐厅的适合程度与原因。
- 确认没有保存精确位置，只在用户主动选择时才有可清除的大致区域。
- 需要真实高德确认时，由用户在服务端配置密钥后运行附近餐厅的实测脚本（见 README 第 20 节）。

## 四、其他情形的一句话处理

- 磁盘满：数据库与上传都可能失败，表现为 internal_error；清理空间后按第一节核对。
- 服务端时钟错误：登录令牌的有效期与到期自动转待复核都依赖日期，时钟明显错误时先校时。
- 多项同时故障：按“数据库、模型服务、高德”的顺序恢复，数据库最先，因为模型服务与高德的核对都要靠登录与读档案，数据库不通就无法核对。
