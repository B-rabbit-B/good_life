# 步骤 06 调用审计说明

每一次通过 SDK 的调用，包括通过 MCP 发来的调用，都会留下一行审计记录，成功的、失败的、被拒绝的都一样。审计用来回答“谁的授权、哪个客户端、什么时候、调用了哪项能力、结果如何”，而不是“传了什么内容、返回了什么内容”。

## 一、记录哪些字段

| 字段 | 含义 |
|---|---|
| 记录编号 | 这一行审计的唯一编号 |
| 用户 | 这次调用代表的用户。凭证无法认证的调用没有用户，这一栏为空 |
| 授权编号 | 使用的是哪一个授权。用用户登录令牌调用时为空；凭证无法认证时为空；授权被吊销后这一栏仍保留，授权记录本身也保留 |
| 凭证类型 | agent_grant（智能体授权令牌）、user_session（用户登录令牌）、none（没有提供有效凭证） |
| 客户端名称 | 调用方自己报的名称，来自 GOODLIFE_CLIENT_NAME，没填时通过 MCP 调用记为 mcp，直接用 SDK 且没填时记为 sdk。只保留可打印字符，最多 64 个字符 |
| 能力名 | 调用的能力，例如 cycle.record_period；最多记 64 个字符 |
| 结果 | ok（成功）或 error（失败，含被拒绝） |
| 错误码 | 失败时的错误码，例如 write_not_granted、invalid_grant、unknown_capability；成功时为空 |
| 耗时 | 这次调用花了多少毫秒 |
| 时间 | 记录的时间 |

## 二、什么情形都会记

- 成功的调用。
- 被业务规则拒绝的调用：未找到、冲突、参数不合法、模块未开放、免责声明未确认。
- 被授权拒绝的调用：只读授权调用写入能力，授权令牌调用需本人确认的能力。
- 凭证有问题的调用：没有令牌、令牌无效、授权过期或被吊销。这类调用没有用户，用户栏为空，因此没有任何用户能在自己的审计里看到它们。
- 能力名不存在的调用，包括模型试图直接请求本文所说不提供的医嘱动作的调用。
- 服务内部出错的调用：错误码是 internal_error。

审计是在每次调用结束时写入的，使用独立的数据库会话：业务操作失败而回滚，不会连带丢掉这一行审计。万一写审计本身失败（例如数据库故障），不会改变这次调用的结果，只会在服务日志里留下一条错误，里面只有能力名与结果，没有任何参数。

## 三、不记录什么，以及原因

- 调用参数：不记。参数里可能有医嘱原文、饮食备注、训练备注、经期日期等敏感内容。
- 返回内容：不记。返回里有用户的健康数据。
- 令牌：不记，也不会出现在服务日志里。授权令牌的明文只在创建时返回一次，数据库里只存哈希。
- 医嘱正文、条目内容、备注：不记。审计表里根本没有存放这类内容的字段，所以不是“记了再脱敏”，而是从设计上不可能带上。
- 错误的具体文字：不记，只记错误码。因为错误文字里有可能带上用户数据。

结果是：审计足以排查“谁在什么时候调用了什么、为什么失败”，但即便被他人看到，也看不到用户的健康内容。

## 四、如何查看自己的审计

在接口文档页面，登录并确认免责声明之后，调用查看调用审计的接口（路径是 /api/agent-grants/audit，方法 GET）。它返回你自己的审计记录，按时间从新到旧；limit 参数控制返回条数，范围是 1 到 200，不填默认 50，超出范围会被拒绝。

返回的每一行包含：记录编号、授权编号、凭证类型、客户端名称、能力名、结果、错误码、耗时、时间。不包含用户这一栏，因为本来就只有你自己的记录。别人的审计，你看不到。这个接口只认用户登录令牌，授权令牌不能用来查看审计。

常见的用法：

- 确认某个客户端最近在做什么：看客户端名称与能力名。
- 确认授权是否被盗用：对照列出授权接口里的“最近使用时间”，看有没有不认识的时间点或客户端。
- 排查失败原因：看错误码，再对照《SDK能力清单》与《接入使用说明》里的错误说明。

## 五、已知限制

- 审计没有自动清理，也没有保留期限设置，会一直保留，直到用户账号被删除时一并删除。
- 凭证无法认证的调用没有用户归属，用户在审计接口里看不到，只有运维人员能在数据库里看到。
- 通过 MCP 调用时，如果工具名对不上任何已提供的工具，MCP 层会把工具名里的点换成下划线再交给 SDK，审计里记下的是换过之后的名字，而不是调用方原样给出的名字；这类调用的错误码一定是 unknown_capability。
- 审计只记录一次调用的概况，不记录一次调用里改动了哪些数据；数据的变更记录由各业务模块自己保存，例如医嘱条目有自己的变更记录。
