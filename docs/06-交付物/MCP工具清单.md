# 步骤 06 MCP 工具清单

本文列出步骤 06 的 MCP 服务对外提供的全部工具，共 27 个，并明确说明不提供的 6 个医嘱动作及原因。MCP 服务只做本地标准输入输出（stdio）方式的协议转换，不含任何业务规则：认证、授权级别、模块准入、参数校验与审计，全部由 SDK 完成，能力的详细含义见《SDK能力清单》，授权与安全的设计见《权限与授权设计说明》，如何接入见《接入使用说明》。

## 一、工具的共同约定

- 命名：工具名是 SDK 能力名把点换成下划线，例如记录一餐的工具名是 nutrition_log_meal。服务名称是 good-life，版本号与 SDK 版本号相同（目前是 1.1）；服务在握手时还会给模型一段使用须知：所有工具都代表令牌对应的用户；给饮食或运动建议之前先读 medical_get_constraints；医嘱的确认、修改、解除只能由用户本人完成，模型最多提出解除建议；只有用户明确要求记录时才调用写入工具。
- 输入字段：每个工具的输入结构（input schema）里，每个字段都带一段中文说明，写明含义、单位（克、分钟、千米、千克、秒）、日期格式（年-月-日）、取值范围与规则，以及编号应当从哪个工具的结果里取。
- 一个工具只做一件事。每个工具的说明由四段组成：这项能力的用途、授权级别、什么时候用、什么时候不要用，再加一句统一的话：所有工具都代表授权令牌对应的用户，不需要也不接受用户编号。下面各节的内容就是这些说明的整理。
- 授权级别：只有“只读”和“写入”两种。写入工具需要用户创建的读写授权，只读授权调用它会被拒绝。需要用户本人确认的动作不是工具，见第四节。
- 用户身份：只来自服务启动时配置的授权令牌，每次调用都重新认证，所以用户在应用里吊销授权后，下一次调用立即失效。工具的输入里没有用户编号这个字段，多填任何多余字段都会被拒绝。别人的记录一律按“未找到”处理。
- 模块准入：与应用里一致。用户没有开放的模块（例如档案性别不是女性时的经期模块）会返回“模块未开放”，免责声明未确认时返回“需要用户本人确认”。
- 结果：每次调用都返回一份结构化的结果，同时以文字和结构化数据两种形式给出，内容相同。成功时包含 ok、sdk_version、data、notices；失败时包含 ok（假）、sdk_version 和 error（类别、错误码、说明、给智能体的建议，参数不合法时还有每个出问题的字段）。失败的调用会被标记为错误，客户端能直接给出可读的提示。数据不足不算错误，会在 notices 里附提示。
- 工具名对不上任何已提供的工具时（包括直接写出 SDK 能力名那种带点的写法，以及需要本人确认的那 6 个动作的名字），一律返回“能力不存在”类的错误，错误码为 unknown_capability，并记入审计。这样即便客户端或模型试图直接请求本文没有提供的动作，也到不了需要本人确认的能力。
- 输出的内容与应用里对应的接口一致，所以读取类工具也会有与接口相同的副作用，例如读取医嘱约束时会先按今天的日期刷新医嘱状态。

## 二、工具一览

下面按模块列出。27 个工具中，只读 22 个，写入 5 个（cycle_record_period、medical_submit_order、medical_propose_resolution、nutrition_log_meal、fitness_log_workout）。

### 档案

**profile_get_capabilities**（授权级别：只读）

- 用途：查看当前用户开放了哪些业务模块（经期、医嘱、饮食、健身）
- 什么时候用：对话开始时、或调用其他工具返回模块未开放时用，先弄清用户开放了经期、医嘱、饮食、健身中的哪些模块
- 什么时候不要用：已经知道模块开放情况时不要反复调用；想看档案详情时改用 profile_get_profile；它不能用来开通模块

**profile_get_profile**（授权级别：只读）

- 用途：查看当前用户档案里与生活方式建议有关的内容：性别、出生年份、身高、体重、活动水平、目标、饮食偏好、忌口食物、可选功能的开关与档案更新时间；不含健康状况与备注
- 什么时候用：给饮食、运动建议前想了解用户的目标、身高体重、活动水平、饮食偏好与忌口食物时用；档案缺项时如实告知，并请用户在应用里补充
- 什么时候不要用：只想知道哪些模块开放时改用 profile_get_capabilities；它不能修改档案；档案里的忌口是用户自填的口味取舍，医嘱约束要用 medical_get_constraints 读取

### 经期

**cycle_get_phase**（授权级别：只读）

- 用途：判断某一天（默认今天）处于经期周期的哪个阶段，以及距下次经期还有几天
- 什么时候用：需要知道某一天（默认今天）处于经期、卵泡期、排卵期还是黄体期，或距下次经期还有几天时用
- 什么时候不要用：想要该阶段的饮食与生活建议时不要用，改用 cycle_get_tips；想看长期统计时改用 cycle_get_stats

**cycle_get_prediction**（授权级别：只读）

- 用途：预测下次经期、排卵日与易孕窗口；记录不足时返回数据不足提示，预测仅供参考
- 什么时候用：用户问下次经期什么时候来、排卵日或易孕窗口时用；回答时说明预测仅供参考，数据不足时如实告知并建议补记
- 什么时候不要用：不要把预测结果当作避孕或备孕的医学依据；只想知道今天处于哪个阶段时改用 cycle_get_phase

**cycle_get_stats**（授权级别：只读）

- 用途：查看经期统计：平均周期长度与波动、最短与最长周期、平均经期天数、近期周期长度和常见症状
- 什么时候用：用户问自己的周期平均多长、规不规律、经期一般几天、常见症状时用
- 什么时候不要用：想知道下次经期或排卵日时不要用，改用 cycle_get_prediction；想知道某天处于哪个阶段时不要用，改用 cycle_get_phase

**cycle_get_tips**（授权级别：只读）

- 用途：获取某一天（默认今天）所处经期阶段的饮食、传统调养与生活方式小贴士
- 什么时候用：用户想知道某一天（默认今天）所处经期阶段该怎么吃、怎么调养、生活上注意什么时用
- 什么时候不要用：评估某种具体食物能不能吃时不要用，改用 nutrition_evaluate_food；不要把小贴士当作医疗建议

**cycle_list_periods**（授权级别：只读）

- 用途：列出用户记录过的全部经期（开始与结束日期），按开始日期从近到远排列
- 什么时候用：用户想回顾自己记录过的经期，或你要核对某次经期是否已经记过、避免重复记录时用
- 什么时候不要用：想看平均周期、规律性等统计时不要用，改用 cycle_get_stats；想知道下次经期时不要用，改用 cycle_get_prediction

**cycle_record_period**（授权级别：写入（需要读写授权））

- 用途：记录一次经期：开始日期必填，结束日期可留空表示仍在经期中
- 什么时候用：用户明确告诉你经期开始（或开始与结束）的具体日期、要求记下来时用；结束日期未知可以留空；记录前先用 cycle_list_periods 确认这次经期没有记过
- 什么时候不要用：日期含糊（如“前几天”）时不要猜，先问清具体日期；只是询问或闲聊经期时不要用

### 医嘱

**medical_get_constraints**（授权级别：只读）

- 用途：查看今天生效的医嘱约束（生效中与待复核的条目），可按类别筛选；给饮食、运动建议前应先读取并遵守
- 什么时候用：给出任何饮食、运动建议之前用，读取今天生效的医嘱约束并严格遵守；用户问“我现在有哪些忌口或限制”时也用
- 什么时候不要用：想看全部历史条目（包括已解除、已作废、待确认的）时不要用，改用 medical_list_items

**medical_get_item**（授权级别：只读）

- 用途：按编号查看一条医嘱条目的详情
- 什么时候用：已经拿到某条医嘱条目的编号、需要查看其完整内容、状态与日期时用
- 什么时候不要用：不知道编号时不要猜，先用 medical_list_items 查找；不要用它批量浏览医嘱

**medical_list_items**（授权级别：只读）

- 用途：列出用户的医嘱条目，可按状态和类别筛选
- 什么时候用：用户想浏览自己的医嘱条目，或你需要按状态、类别查找某条医嘱的编号时用
- 什么时候不要用：只想知道今天必须遵守哪些限制时不要用，改用 medical_get_constraints；已经知道编号想看详情时改用 medical_get_item

**medical_list_reviews**（授权级别：只读）

- 用途：列出需要用户处理的医嘱条目：到期待复核的，以及有待处理解除建议的
- 什么时候用：提醒用户哪些医嘱到期需要复核、哪些有待处理的解除建议时用
- 什么时候不要用：不要替用户完成复核或确认，复核结果只能由用户本人在应用里处理；想看今天的约束时改用 medical_get_constraints

**medical_propose_resolution**（授权级别：写入（需要读写授权））

- 用途：对生效中或待复核的医嘱条目提出解除建议并说明理由；只是建议，约束保持不变，解除与否由用户本人确认
- 什么时候用：用户说医生已允许停止某条医嘱（例如复查后解除限制），需要提出解除建议并写明理由时用；只是建议，用户在应用里确认后才会解除，在此之前约束照常生效
- 什么时候不要用：不要仅凭自己的判断或用户的随口一说就提出解除；不能用它代替用户确认，也不能用来修改或作废医嘱，这些只能由用户本人在应用里操作

**medical_submit_order**（授权级别：写入（需要读写授权））

- 用途：提交一段医嘱原文，系统从中提取条目；提取出的条目只是待用户本人确认的状态，确认之前不会成为生效的约束
- 什么时候用：用户提供医生的医嘱、病历或复诊单原文、希望录入时用；只会生成待用户确认的条目，不会立即生效，提交后提醒用户到应用里逐条确认
- 什么时候不要用：不要自己编写或改写医嘱内容再提交，只提交用户给出的原文；用户只是询问已有医嘱时不要用，改用 medical_list_items 或 medical_get_constraints

### 饮食

**nutrition_evaluate_food**（授权级别：只读）

- 用途：结合医嘱约束、经期阶段、目标、训练与今日摄入等，评估用户今天吃某种食物（不填分量时按默认份量）是否合适并说明理由
- 什么时候用：用户问“这个能不能吃”“吃这么多行不行”等关于单种食物的问题时用；需要先用 nutrition_search_foods 拿到食物编号，它会按给定分量（不填则按默认份量）综合医嘱约束、经期阶段、目标、训练与今日摄入给出结论和理由
- 什么时候不要用：不要用它推算“吃多少最合适”，它只评估给定的分量；用户已经吃了、要求记录时改用 nutrition_log_meal；一餐里有多种食物时改用 nutrition_evaluate_meal

**nutrition_evaluate_meal**（授权级别：只读）

- 用途：结合医嘱约束、经期阶段、目标、训练与今日摄入等，评估一餐中的多种食物是否合适，给出逐项与整体结论
- 什么时候用：用户想评估一餐中的多种食物（如一份套餐或一桌菜）是否合适时用，会给出逐项与整体结论
- 什么时候不要用：只问单种食物时改用 nutrition_evaluate_food；用户已经吃完要求记录时不要用，改用 nutrition_log_meal

**nutrition_get_daily_summary**（授权级别：只读）

- 用途：汇总某一天（默认今天）各餐与全天的营养摄入，并对照估算的每日需求给出剩余量；档案不完整时无法估算需求
- 什么时候用：用户问某一天（默认今天）吃了多少热量、蛋白质等，以及距离每日需求还剩多少时用；档案不完整无法估算需求时如实告知并引导补充
- 什么时候不要用：想看逐条饮食明细时不要用，改用 nutrition_list_meals；不要用它判断某种食物能不能吃

**nutrition_get_food**（授权级别：只读）

- 用途：按编号查看一种食物的详情：每 100 克营养素、标签、常用份量与数据来源
- 什么时候用：已经拿到食物编号、需要查看每 100 克营养素、标签、常用份量与数据来源时用
- 什么时候不要用：不知道编号时不要猜，先用 nutrition_search_foods；想判断用户今天能不能吃时不要用，改用 nutrition_evaluate_food

**nutrition_list_meals**（授权级别：只读）

- 用途：列出某一天（默认今天）记录的全部饮食及各项营养素
- 什么时候用：用户想看某一天（默认今天）具体记录了哪些饮食及每项的营养素时用
- 什么时候不要用：只想知道全天总摄入和还剩多少额度时不要用，改用 nutrition_get_daily_summary

**nutrition_log_meal**（授权级别：写入（需要读写授权））

- 用途：记录用户吃过的一项食物：日期、餐次、食物编号，克数与份量必须且只能填一项
- 什么时候用：用户明确说吃了什么、吃了多少（克数或份量）、要求记下来时用；每次记录一项食物，克数与份量只填一项
- 什么时候不要用：只是询问能不能吃时不要用，改用 nutrition_evaluate_food；分量不明确时先问清楚，不要自己编造分量

**nutrition_search_foods**（授权级别：只读）

- 用途：按名称或别名搜索食物库，返回候选食物及其编号；没有完全一致的结果时需与用户确认是哪一种
- 什么时候用：用户提到某种食物、需要找到它在食物库里的编号时用（记录饮食、评估食物之前通常先调用）；有多个候选时与用户确认是哪一种
- 什么时候不要用：已经知道食物编号时不要重复搜索；想看某种食物的营养详情时改用 nutrition_get_food

### 健身

**fitness_get_exercise_trend**（授权级别：只读）

- 用途：查看某个力量动作按日的进步趋势：最大重量、总训练量、总次数与组数
- 什么时候用：用户想知道某个力量动作的进步情况（最大重量、训练量的变化）时用；需要先拿到动作编号
- 什么时候不要用：不知道动作编号时先用 fitness_search_exercises；不适用于有氧动作或整体训练回顾

**fitness_get_training_signal**（授权级别：只读）

- 用途：查看用户今天的训练情况：是否训练、强度、练到的肌群、估算消耗与医嘱冲突，供饮食建议参考
- 什么时候用：给饮食建议前想知道用户今天是否训练、强度如何、练了哪些肌群、估算消耗多少时用
- 什么时候不要用：想回顾过去的训练时不要用，改用 fitness_list_workouts 或 fitness_get_week_summary

**fitness_get_week_summary**（授权级别：只读）

- 用途：汇总一周（开始日期须为星期一，默认本周）的训练次数、训练天数、训练量、各肌群训练量、有氧分钟数与估算消耗
- 什么时候用：用户想了解某一周（默认本周）练了几次、训练量、各肌群分布、有氧时长与估算消耗时用；开始日期必须是星期一，查上周或其他某周时先换算成那一周的星期一再填
- 什么时候不要用：想看逐条训练明细时不要用，改用 fitness_list_workouts；想看跨多周或任意日期段的记录时也改用 fitness_list_workouts

**fitness_list_workouts**（授权级别：只读）

- 用途：列出一段日期内的训练记录（结束日期默认今天，开始日期默认为结束日期及之前共 7 天；开始不能晚于结束，最多 366 天），每条附带与运动限制医嘱的冲突提示
- 什么时候用：用户想回顾一段日期内（默认最近 7 天）的训练记录及其与医嘱的冲突提示时用
- 什么时候不要用：只想看某周的汇总数据时不要用，改用 fitness_get_week_summary；只关心今天的训练对饮食的影响时改用 fitness_get_training_signal

**fitness_log_workout**（授权级别：写入（需要读写授权））

- 用途：记录一次训练：日期、时长、主观强度、力量动作的每组重量与次数、有氧动作的时长与距离；与运动限制医嘱冲突时只提示不阻止
- 什么时候用：用户明确说完成了一次训练、给出了日期、动作及组数次数或时长、要求记下来时用；与运动限制医嘱冲突时会返回提示，要如实转告用户
- 什么时候不要用：用户只是计划或询问训练时不要用；重量、次数等关键信息缺失时先问清楚，不要自己编造

**fitness_search_exercises**（授权级别：只读）

- 用途：按名称或别名搜索动作库（含用户自定义动作），返回候选动作及其编号；没有完全一致的结果时需与用户确认是哪一个
- 什么时候用：用户提到某个训练动作、需要找到它在动作库里的编号时用（记录训练、查看动作趋势之前通常先调用）；有多个候选时与用户确认是哪一个
- 什么时候不要用：已经知道动作编号时不要重复搜索；不要用它推荐训练计划

## 三、典型的工具组合

- 记录一餐：先 nutrition_search_foods 找到食物编号，有多个候选时请用户确认，再 nutrition_log_meal。
- 评估一种食物：先 nutrition_search_foods，再 nutrition_evaluate_food；评估之前模型应当已经读取过 medical_get_constraints。
- 记录训练：先 fitness_search_exercises 找到动作编号，再 fitness_log_workout，如果返回里有与医嘱运动限制的冲突提示，要如实转告用户。
- 录入医嘱：medical_submit_order 只会生成待用户确认的条目；提醒用户到应用里逐条确认之后，条目才会成为生效的约束，medical_get_constraints 才会读到。

## 四、不提供的 6 个医嘱动作及原因

下面 6 个动作在 SDK 里存在，授权级别是“需用户本人确认”，但不注册为 MCP 工具：确认一条待确认的医嘱条目、修改一条医嘱条目、解除一条医嘱条目、作废一条医嘱条目、让待复核的条目继续生效、撤回解除建议。它们与医嘱模块里“只能由用户本人操作”的动作一一对应。

不提供的原因：

1. 医嘱是用户对自己健康的约束，一旦确认就会影响饮食与运动的判断，解除则会放宽这些约束。这两类决定不能由模型代为做出，也不能因为模型误解了一句话而发生。
2. 令牌只代表“用户授权了智能体读取或写入”，并不代表“用户在这一刻确认了这件事”。所以即使这些动作在 SDK 里被调用，授权令牌也一律被拒绝，只有用户本人的登录令牌可以。
3. 模型能做的最大限度是提出解除建议（medical_propose_resolution）：它只记录建议与理由，条目状态与约束保持不变，等用户在应用里确认之后才会真正解除。

这一点由三道关口共同保证：MCP 不注册这些工具；万一客户端直接发来相应的名字，会被当作不存在的能力拒绝并记入审计；即便走到 SDK，授权令牌也不能调用需本人确认的能力。

## 五、失败时模型应当怎么做

| 错误类别 | 模型应当怎么做 |
|---|---|
| 参数不合法 | 对照字段说明修正后重试；能力不存在时，只使用本文列出的工具 |
| 未找到 | 先用搜索或列表类工具确认编号，不要猜编号 |
| 禁止 | 如实告诉用户当前授权只允许读取，请用户创建读写授权；不要换着方式重试 |
| 未认证 | 告诉用户授权无效、已过期或已吊销，请用户重新创建授权并更新令牌 |
| 需要用户本人确认 | 告诉用户这一步必须由本人在应用里完成，例如确认免责声明、确认医嘱 |
| 冲突 | 先查询最新状态，再决定是否重试 |
| 模块未开放 | 先调用 profile_get_capabilities 看哪些模块开放，如实告诉用户 |
| 内部出错 | 读取类工具可以稍后重试一次；写入类工具不要直接重试，数据可能已经保存，先用对应的列表工具核对；仍失败就告诉用户，不要编造结果 |

八个类别的完整说明见《SDK能力清单》第六节。
