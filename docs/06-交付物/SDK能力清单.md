# 步骤 06 SDK 能力清单

本文列出步骤 06 的进程内 SDK 对外开放的全部能力，共 32 项，当前 SDK 版本号为 1.0。每一项都写明用途、授权级别、输入含义、输出含义、可能的失败与数据不足时的提示。本文只用自然语言描述，不放代码。

SDK 是领域能力的稳定外壳：它直接在后端进程内调用步骤 02 至 05 已有的接口函数，所以校验、业务规则与输出内容与对应的 REST 接口只有一份实现，不会各走各的。SDK 自己负责四件事：稳定的能力名、统一的输入参数、统一的错误结构，以及版本号。MCP 服务只是 SDK 之上很薄的一层协议转换，见《MCP工具清单》。

## 一、一次调用的完整过程

调用入口是后端 app.sdk 包里的 GoodLife 对象。每次调用需要给出三样东西：凭证、能力名、输入参数（可以没有），另可附带一个客户端名称，用于审计。每次调用都会重新认证，不缓存任何登录状态。处理顺序是固定的，前一步不通过就不会进入下一步：

1. 认证：凭证只能是两种之一，用户签发给智能体的授权令牌（以 gl_ 开头），或用户本人的登录令牌。没有凭证、凭证无效、授权已过期或已吊销、登录令牌已失效，都按“未认证”处理。
2. 查能力名：能力名不在清单里，返回“能力不存在”。注意这一步在认证之后、免责声明检查之前。
3. 查授权级别：需要本人确认的能力，授权令牌一律拒绝；写入类能力，只读授权拒绝。
4. 查免责声明与模块准入：先要求用户已确认当前版本的免责声明，再按步骤 01 的能力清单检查对应模块是否对该用户开放，规则与 REST 接口完全一致。查看模块开放情况的那一项能力只要求免责声明。
5. 校验参数：所有输入都拒绝多余字段，任何能力都不接受用户编号。
6. 执行：调用对应的接口函数。
7. 序列化：输出按能力声明的类型校验后转成普通数据。输出不符合声明的类型属于服务内部出错，不是调用方的错。
8. 附加提示：数据不足这类情形不算错误，会在成功结果里附带提示，见第五节。
9. 审计：无论成功还是失败，都记一行审计，见《调用审计说明》。

用户身份只来自凭证，没有任何地方可以填“代表哪个用户”。别人的记录一律按“未找到”处理，与不存在的记录无法区分。

写入业务事件时的来源也由凭证决定：用授权令牌提出医嘱解除建议，记录的来源是“智能体”；用用户登录令牌，记录的来源是“用户”。

读取类能力与对应的 REST 接口有相同的副作用，这一点不是 SDK 新增的：医嘱模块的准入检查，以及读取医嘱约束的能力（包括饮食评估和训练记录在计算冲突时），和 REST 一样会先按今天的日期刷新医嘱条目的状态，例如到期转为待复核、过期自动作废；查看模块开放情况会在用户还没有档案时创建一份空档案。

## 二、授权级别

| 级别 | 含义 | 哪些凭证可以调用 |
|---|---|---|
| read（只读） | 只读取数据，不改变业务数据 | 只读授权、读写授权、用户登录令牌 |
| write（写入） | 新增数据，或写入“建议” | 读写授权、用户登录令牌；只读授权被拒绝 |
| user_confirmed（需用户本人确认） | 医嘱的确认、修改、解除、作废、继续生效、撤回解除建议 | 只有用户登录令牌；任何授权令牌都被拒绝 |

共 32 项：只读 21 项、写入 5 项、需用户本人确认 6 项。需用户本人确认的 6 项只在 SDK 里存在，不会注册为 MCP 工具。

## 三、统一的结果结构

成功的结果包含四部分：ok（真）、sdk_version（SDK 版本号）、data（能力的输出）、notices（提示列表，没有就是空列表）。每条提示有 kind（目前只有 insufficient_data）与 message（给人读的说明）。

失败的结果包含 ok（假）、sdk_version，以及 error。error 里有五个字段：

- kind：错误类别，共八种，见第六节，供智能体按类别分支处理。
- code：具体的错误码，沿用业务模块的错误码，或 SDK 自己的错误码。
- message：给人读的中文说明。
- hint：给智能体的下一步建议，每个类别都有默认建议，个别错误码有更具体的建议。
- details：只有参数不合法时才有，列出每个出问题的字段名与原因；其他情形为空。

## 四、能力一览

“输入”一栏只写含义。日期一律是“年-月-日”的写法；所有输入都不含用户编号；带“可不填”的字段可以省略。“输出”一栏描述返回内容的含义，字段与对应 REST 接口的响应一致，完整的字段结构见仓库里的能力清单快照文件 backend/app/sdk/manifest.json。“失败”一栏只列这项能力特有的主要错误码；所有能力共有的失败见第六节。

## 五、数据不足时的提示

数据不足不是错误：这些情形下仍有数据可用，所以结果照常返回，同时在提示列表里附一条 insufficient_data 类的提示。智能体应当如实告知用户，并引导用户补充数据，不要自己编造数字。

| 能力名 | 什么时候附提示 | 提示的意思 |
|---|---|---|
| cycle.get_prediction | 预测状态是“数据不足”，包括一条经期记录都没有的情形 | 经期记录还不够，暂时无法预测，可以请用户补充最近几次经期 |
| cycle.get_phase | 无法判断的原因是“数据不足”，或者“还没有任何经期记录” | 同上；没有任何记录时，提示明确写“还没有经期记录” |
| nutrition.get_daily_summary | 档案不完整、无法估算每日需求 | 列出缺少的档案字段（出生年份、身高、体重、活动水平），请用户补充 |
| fitness.get_week_summary | 档案里没有体重，无法估算训练消耗 | 档案里没有体重，无法估算训练消耗 |
| fitness.get_training_signal | 同上 | 同上 |

孕期或暂停记录导致的“已暂停”状态不属于数据不足，不附提示，由结果里的状态说明。

## 六、错误结构与八个错误类别

错误类别是稳定的，智能体应当按类别分支处理，而不是解析错误文字。

| 类别 | 含义 | 常见错误码 | 给智能体的建议 |
|---|---|---|---|
| invalid_input | 参数不合法或能力名不存在 | validation_error（参数不合法，details 列出每个字段）、unknown_capability（能力不存在）、各模块的 422 类业务错误码 | 按能力的输入说明修正参数后重试；能力不存在时先列出可用能力再使用其中的名称 |
| not_found | 记录不存在，或不属于当前用户 | not_found、food_not_found、exercise_not_found | 先用列表或搜索类能力确认编号，不要猜 |
| forbidden | 当前凭证不允许这项操作 | write_not_granted（只读授权调用写入能力） | 如实告知用户，不要换着方式重试；需要写入时请用户创建读写授权 |
| unauthenticated | 凭证缺失、无效、过期或已吊销 | missing_credential、invalid_grant、invalid_token | 让用户在应用里重新创建授权 |
| needs_user_confirmation | 这一步需要用户本人完成 | user_confirmation_required（需本人确认的能力）、disclaimer_not_accepted（免责声明未确认，提示请用户先在应用里阅读并确认） | 如实告知用户，由用户本人在应用里完成；解除医嘱只能提出建议 |
| conflict | 与已有数据冲突 | period_overlap、invalid_transition、item_closed、no_proposal | 先查询最新状态，再决定是否重试 |
| module_unavailable | 对应模块对当前用户未开放 | cycle_not_available 等各模块的 not_available 错误码 | 先调用 profile.get_capabilities 查看可用模块，不要反复尝试 |
| internal | 服务内部出错，包括输出不符合声明的类型 | internal_error | 稍后重试，仍失败时告知用户；错误信息不会暴露内部细节 |

业务错误按 HTTP 状态映射：401 对应未认证；403 且错误码以 not_available 结尾对应模块未开放；403 且错误码是免责声明未确认对应需本人确认；其他 403 对应禁止；404 对应未找到；409 对应冲突；400、413、415、422 对应输入不合法；其余一律归为内部出错。

## 七、版本与向后兼容

SDK 版本号目前是 1.0，出现在每一个成功与失败的结果里，调用方可以据此判断能力清单的版本。

仓库里保存着一份能力清单快照（backend/app/sdk/manifest.json），记录每项能力的名称、模块、级别、说明，以及输入与输出的完整结构。自动化测试把当前注册的能力与快照逐项比对：任何变化，包括 REST 响应结构的变化传导到 SDK 输出，测试都会失败，必须同时更新快照，也就是变更必然留下记录，不会悄悄发生。

向后兼容的约定如下。这是人工遵守的约定，自动化测试只负责发现“有变化”，不会自动判断变化是否兼容：

- 兼容的变更：新增能力、新增可不填的输入字段、输出里新增字段、补充说明文字。这类变更提高小版本号。
- 不兼容的变更：删除或改名能力、删除输出字段或改变其含义、新增必填输入、改变授权级别、改变错误类别的含义。这类变更提高大版本号，并在文档里写明迁移办法。
- 能力的名称一经发布不重复使用，不改变含义。
- 任何授权级别的调整，不论变严还是变松，都按不兼容变更处理，因为它直接影响安全。

## 八、已知限制

- 有效授权最多 20 个的限制，在同时创建时没有做串行化处理，并发创建可能略微超出，不影响安全。
- 审计里记录的是能力名。通过 MCP 调用时，如果工具名对应不上任何已暴露的工具，MCP 层会把工具名里的点换成下划线再交给 SDK，审计里记下的就是换过之后的名字，而不是调用方原样给出的名字。
- 读取类能力的副作用与 REST 相同（见第一节），SDK 没有额外屏蔽。
- SDK 目前是进程内调用，没有独立的网络服务。设计约定：步骤 08 的智能体在后端内部使用 SDK 时，必须使用用户签发的授权令牌，而不是用户登录令牌；这一点由约定保证，SDK 本身并不阻止调用方传入登录令牌。
