# 步骤 06 权限与授权设计说明

本文说明智能体如何获得权限、权限能做什么、不能做什么，特别是医嘱确认与解除的处理方式。一句话概括：智能体只能拿到用户明确签发的、可随时收回的授权；读与写分开授权；医嘱这类关键决定，永远只能由用户本人在应用里做出，智能体最多提出建议。

## 一、两种令牌

| | 用户登录令牌 | 智能体授权令牌 |
|---|---|---|
| 怎么得到 | 用户用账号密码登录得到 | 用户登录后，在应用里主动创建，创建时指定名称、权限、有效期 |
| 代表什么 | 用户本人在操作 | 用户允许某个智能体在限定范围内代为读取或写入 |
| 形式 | 登录接口返回的访问令牌 | 以 gl_ 开头的随机串 |
| 可用于 | 应用里的全部接口；也可以用于 SDK | 只能用于 SDK 与 MCP；不能用来访问应用的接口，也不能用来创建、查看、吊销授权 |
| 能调用需本人确认的能力吗 | 能 | 不能，一律拒绝 |
| 怎么失效 | 登出、过期，或密钥更换 | 过期或被用户吊销；用户登出不会让它失效 |

两者必须分开的原因：登录令牌能做用户本人能做的一切，包括确认与解除医嘱；授权令牌是用户交给第三方程序的，万一泄露或被模型误用，影响范围必须限定在用户事先划定的边界内。所以步骤 08 的智能体在后端内部使用 SDK 时，必须使用授权令牌，而不是用户登录令牌（这是设计约定，SDK 本身并不阻止调用方传入登录令牌，需要在步骤 08 的实现与验收时守住）。

## 二、授权的签发、权限、有效期与吊销

- 签发：用户登录并确认免责声明之后，在接口文档页面创建授权。创建时填写名称（1 到 50 字，例如客户端的名字）、权限和有效期。创建接口不接受用户编号，授权只属于当前登录的用户。
- 权限：只有两种。“只读”只能调用只读能力；“读写”可以调用只读与写入能力。没有任何授权级别能调用需本人确认的能力。想给一个只想让它查看数据的客户端用，就创建只读授权；想让它代为记录，就创建读写授权，两者可以分别创建、分别吊销。
- 有效期：1 到 365 天，不填默认 90 天，到期自动失效，不能续期，需要时重新创建。
- 数量：每个用户同时有效的授权最多 20 个，超过会被拒绝，错误码 too_many_grants，需要先吊销不用的授权。
- 令牌只显示一次：令牌明文只在创建授权的那一次响应里返回，之后任何接口都查不到。这次响应带有禁止缓存的标记，浏览器与中间代理都不应保存它。遗失后只能吊销并重新创建。
- 只存哈希：数据库里保存的是令牌的哈希值，不是令牌本身，也不保存任何可以还原令牌的信息，所以即使数据库泄露也无法直接拿到可用的令牌。令牌也不会写进日志或审计记录。
- 查看：列出授权时只显示名称、权限、状态（有效、已过期、已吊销）、有效期、创建时间、吊销时间与最近使用时间，不显示令牌。
- 吊销：用户随时可以吊销自己的授权，吊销立即生效：下一次调用就会被拒绝。每次调用都重新核对授权，没有缓存。吊销是软删除，授权记录保留，审计里仍能对应到它。
- 隔离：用户只能看到、吊销自己的授权，别人的授权按“未找到”处理。

## 三、用户身份只来自凭证

- 任何能力、任何 MCP 工具都不接受用户编号，请求里多带了用户编号这类多余字段，会被当作参数不合法拒绝。
- 一次调用代表哪个用户，完全由凭证决定：授权令牌属于哪个用户，就代表哪个用户。
- 别人的数据一律按“未找到”处理：用别人的记录编号去读取、修改，得到的结果和编号不存在完全相同，不暴露它是否存在。
- 没有凭证或凭证无效，调用被拒绝，类别是“未认证”，同样会记入审计。

## 四、授权级别与处理顺序

| 级别 | 谁能调用 |
|---|---|
| 只读 | 只读授权、读写授权、用户登录令牌 |
| 写入 | 读写授权、用户登录令牌；只读授权被拒绝（错误码 write_not_granted） |
| 需用户本人确认 | 只有用户登录令牌；授权令牌被拒绝（错误码 user_confirmation_required） |

处理顺序是：先认证，再查能力名，再查级别，然后才是免责声明与模块准入、参数校验。所以不论写入类能力的参数对不对，只读授权都会先被拒绝；不论用户是否已确认免责声明、参数是否合法，授权令牌调用需本人确认的能力都会先被拒绝。

模块准入与应用里完全一致：先要求用户已确认当前版本的免责声明，再检查该模块是否对用户开放。授权令牌不能绕过这两关。

## 五、医嘱确认与解除的处理方式

医嘱模块里有六个只能由用户本人操作的动作：确认条目、修改条目、解除条目、作废条目、让待复核的条目继续生效、撤回解除建议。处理方式分三层：

1. SDK：这六个动作在 SDK 里存在，级别是“需用户本人确认”，只认用户登录令牌。用授权令牌调用，返回“需要用户本人确认”类的错误，提示里告诉智能体这一步只能由用户本人在应用里操作，如需解除可以提出建议。
2. MCP：这六个动作不注册为工具。工具列表里没有它们；万一客户端直接请求它们的名字，也会被当作不存在的能力拒绝并记入审计。
3. 应用：用户本人在接口文档页面（以后是前端页面）登录后，用医嘱接口完成确认、修改、解除等操作。

智能体能做的只有三件与医嘱有关的事：

- 提交医嘱原文（medical_submit_order）：只会生成“待确认”状态的条目，在用户本人确认之前，它们不是生效的约束，不影响饮食与运动判断。
- 读取：查看条目、当前约束、待复核与有待处理解除建议的条目。
- 提出解除建议（medical_propose_resolution）：只记录建议和理由，条目的状态与约束保持不变，仍然生效；建议会在“需要用户处理”的列表里出现，由用户在应用里决定是解除还是撤回建议。

提出解除建议时，医嘱的变更记录里会写明建议的来源：通过授权令牌提出的，来源是“智能体”；用户本人的登录令牌通过 SDK 提出的，来源是“用户”。这样事后可以区分哪些建议是智能体提的。

## 六、没有做的事与已知限制

- 不做面向第三方开发者的开放平台、计费与密钥管理：授权只在用户与自己的智能体之间使用。
- 只做本地 stdio 传输：令牌由环境变量提供，不经过网络传输；不提供远程访问的方式，也没有跨机器的认证。
- 令牌保存在客户端的配置里（环境变量），谁能读取这份配置，谁就能使用这个授权。所以建议为每个客户端单独创建授权、优先用只读授权、设置较短的有效期，不用时及时吊销。
- 同时有效的授权数量上限（20 个）的检查没有做串行化处理，并发创建时可能略微超出，不影响安全。
- 授权不会因为用户登出而被吊销（已知限制）：登出只让登录令牌失效，已签发的智能体授权在到期前仍然有效。不再使用某个客户端、或怀疑令牌泄露时，请在授权管理处（目前是接口文档页面里的吊销授权接口）逐个吊销。
