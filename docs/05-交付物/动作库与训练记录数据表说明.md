# 步骤 05 动作库与训练记录数据表说明

本文说明步骤 05 新增的四张数据表，以及不入数据库的内置动作库的字段与规模。表结构由数据库迁移脚本统一管理：迁移编号 0010 接在步骤 04 的最后一个迁移（0009）之后，一次建出四张表。按顺序执行全部迁移，即可在空库中建出全部十六张表。

阅读约定与前几步的数据表说明一致：

- “是否必填”指数据库层面该列能否为空。
- “是否加密”指该列存入数据库时是否已被加密，加密后在数据库里只能看到密文，需要持有加密密钥才能还原。
- 所有时间列都带时区；日期列只有年月日，没有时区。
- 四张表都带 user_id 列，指向 users 的 id，并建有索引；用户被删除时，其健身数据一并删除。所有查询都从“只查当前用户的数据”开始，别人的记录与不存在的记录一样返回 404，不暴露记录是否存在。
- 任何接口都不接受客户端传入用户编号。

## 一、整体结构

- 内置动作库是只读的参考数据，随程序从数据文件加载进内存，不写入数据库，所以数据库里没有内置动作的表；内置动作的编号形如 ex:running（前缀 ex: 加英文标识）。
- 用户自己新增的动作存在 custom_exercises 表，只对本人可见，编号形如 custom: 加一串唯一编号。
- 一次训练（workouts）下面挂零到多条力量训练的“组”（strength_sets）和零到多条有氧记录（cardio_entries）。一次训练至少要有一个力量动作或一个有氧项目。
- 训练被删除时，它的组与有氧记录一并删除（数据库外键设置了级联删除）。自定义动作被删除时，历史训练里的动作名称仍然保留（见下文“动作名称快照”）。

## 二、custom_exercises（自定义动作）

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 动作唯一标识 | 是（主键） | 否 | 随机生成的唯一编号；对外的动作编号是“custom:”加这个编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| name | 动作名称 | 是 | 否 | 1 到 64 个字符，首尾空白会被去掉；同一用户下名称不能重复（数据库唯一约束），重复时返回 409 |
| aliases | 别名列表 | 是 | 否 | 最多 10 个，每个 1 到 32 个字符，不填为空列表 |
| kind | 类型 | 是 | 否 | strength（力量）或 cardio（有氧） |
| primary_muscles | 主要肌群 | 是 | 否 | 至少 1 个，取值见下文肌群表 |
| equipment | 器械类型 | 是 | 否 | 取值见下文器械表 |
| traits | 训练特征 | 是 | 否 | 可不填，取值见下文特征表；医嘱运动限制的冲突判断要用，自定义动作由用户自行标注 |
| met_light、met_moderate、met_vigorous | 轻度、中等、高强度下的代谢当量 | 有氧动作必填，力量动作必须为空 | 否 | 每个大于 0 且不超过 30，并且由轻到高不递减；力量动作不填，估算时统一按力量训练的取值 |
| created_at | 创建时间 | 是 | 否 | 创建时由数据库自动填写 |

动作的名称、别名、肌群等只是动作的描述，不属于敏感的身体数据，所以明文存储，检索时直接比较。

## 三、workouts（一次训练）

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 训练唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| performed_on | 训练日期 | 是 | 否 | 日期；不能晚于“今天”，可以补录过去的日期。建有按用户与日期的联合索引，汇总与按日期范围查询都靠它 |
| duration_minutes | 整次训练时长（分钟） | 否 | 否 | 1 到 600；填了之后，力量部分的时长按“总时长减有氧时长”估算，见《训练量与能量估算口径说明》 |
| rpe | 整次训练的主观强度 | 否 | 否 | 1 到 10；没填按中等 |
| note | 备注 | 否 | 是 | 最多 500 个字符；加密存入 |
| created_at | 记录时间 | 是 | 否 | 创建时由数据库自动填写 |
| updated_at | 最近修改时间 | 是 | 否 | 每次整条替换时更新 |

## 四、strength_sets（力量训练的一组）

每一行是一次训练里某个动作的一组。同一个动作的多组用相同的 position（动作在本次训练中的顺序）和不同的 set_index（组序）区分。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 组的唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| workout_id | 所属训练 | 是 | 否 | 指向 workouts 的 id，并建有索引；训练被删除时一并删除 |
| exercise_id | 动作编号 | 是 | 否 | 内置动作或自定义动作的编号；不设外键，因为内置动作不在数据库里，自定义动作也允许被删除 |
| exercise_name | 动作名称快照 | 是 | 否 | 记录时的名称；之后动作改名或被删除，历史记录里的名称不变 |
| position | 动作顺序 | 是 | 否 | 从 1 开始，是这个动作在本次训练力量部分的顺序 |
| set_index | 组序 | 是 | 否 | 从 1 开始，是这一组在该动作里的顺序 |
| weight_kg | 重量（千克） | 是 | 否 | 0 到 500；自重动作记 0 |
| reps | 次数 | 是 | 否 | 1 到 100 |
| rest_seconds | 这一组之后的休息时间（秒） | 否 | 否 | 0 到 900；没填时估算用 90 秒 |
| rpe | 这一组的主观强度 | 否 | 否 | 1 到 10 |

一个动作最多 30 组，一次训练最多 30 个力量动作。

## 五、cardio_entries（有氧记录）

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 记录唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| workout_id | 所属训练 | 是 | 否 | 指向 workouts 的 id，并建有索引；训练被删除时一并删除 |
| exercise_id | 动作编号 | 是 | 否 | 同上，不设外键 |
| exercise_name | 动作名称快照 | 是 | 否 | 同上 |
| position | 顺序 | 是 | 否 | 从 1 开始，是它在本次训练有氧条目中的顺序 |
| duration_minutes | 时长（分钟） | 是 | 否 | 1 到 600 |
| distance_km | 距离（千米） | 否 | 否 | 0 到 300 |
| rpe | 主观强度 | 否 | 否 | 1 到 10；没填时沿用整次训练的主观强度 |

一次训练最多 30 条有氧记录。

## 六、哪些加密，哪些明文，为什么

- 加密的只有训练备注（workouts 的 note）。备注是用户自由书写的文字，可能写到身体状况、伤病或情绪，属于敏感内容，和档案备注、饮食备注一样用同一个字段加密密钥加密。加密密钥的保管提醒见仓库根目录 README。
- 动作、组数、重量、次数、时长、主观强度、日期全部明文。原因是汇总与趋势需要在数据库里按日期范围查询、按动作筛选，并做数值计算；如果加密，只能把全部记录读出来解密后再算，既慢又不便于建索引。这些数值单独拿出来不含自由文字，风险低于备注。
- 自定义动作的名称与别名同样明文：检索要直接比较。
- 隔离靠 user_id：所有查询都先限定当前用户，不依赖加密。

## 七、动作名称快照与删除

训练记录里保存的是记录当时的动作名称。用户删除自定义动作后：

- 历史训练记录仍然能正常读取，动作名称不变；
- 汇总里这个动作的肌群按“全身”计算，有氧动作因为拿不到代谢当量而不计入能量估算，汇总的说明里会写明；
- 查询这个动作的趋势仍然可以，只要用户的训练里用过它；
- 与医嘱运动限制做冲突判断时，已删除的自定义动作按“特征未知”处理，给出“无法判断”。

## 八、内置动作库

内置动作库是数据文件，由自己整理，不拷贝任何开源项目的数据。共 56 个动作：力量动作 40 个，有氧动作 16 个。每个动作的字段如下。

| 字段 | 含义 | 说明 |
|---|---|---|
| 编号 | 动作唯一标识 | 英文小写加下划线，对外加前缀 ex:，例如 ex:bench_press；编号不重复 |
| 名称 | 中文名称 | 例如卧推、站姿推举、跑步、游泳 |
| 别名 | 常见的其他叫法 | 可以为空；例如卧推有杠铃卧推、平板卧推，站姿推举有站姿杠铃推举、杠铃推举，跑步有户外跑 |
| 类型 | 力量或有氧 | 40 个力量，16 个有氧 |
| 主要肌群 | 主要锻炼的肌群 | 至少 1 个 |
| 器械类型 | 用什么器械 | 见器械表 |
| 训练特征 | 医嘱运动限制判断用 | 可以为空，例如跑步有“跑步”，波比跳有“跳跃”与“高冲击” |
| 代谢当量 | 有氧动作在轻度、中等、高强度下的取值 | 只有有氧动作有，三个数由轻到高不递减；力量动作没有，统一按力量训练取值 |

启动时数据文件会被严格校验：字段多余、取值不在允许范围、编号重复、有氧动作缺代谢当量、代谢当量不是由轻到高不递减、力量动作带了代谢当量，都会直接拒绝加载。

### 检索规则

检索时先把输入和动作名称、别名都去掉空白并统一大小写，再按下面的层级由高到低排序：名称完全相同（exact_name）、别名完全相同（exact_alias）、名称或别名以输入开头（prefix）、名称或别名包含输入（contains）、输入包含名称或别名（query_contains，名称至少 2 个字符，例如输入“杠铃卧推训练”命中卧推）。层级相同时，内置动作排在自定义动作前，再按名称长度、编号排序，所以结果是确定的。最多返回 20 个。

返回里的“完全一致”表示排在第一的结果命中方式是名称完全相同或别名完全相同。只有名称相近的候选时，提示“没有完全一致的动作，下面是名称相近的候选，请确认是否是你要找的”；没有任何命中时，提示“未找到……可以新增自定义动作”，不会猜一个相近的动作。

### 来源与授权

- 动作库由自己整理，没有拷贝任何开源项目的代码或数据。参考的是 wger 一类项目的“动作加别名加肌群加器械”的表结构思路，该项目为强传染许可，所以只参考思路。
- 有氧动作的代谢当量参照公开的身体活动代谢当量表（Compendium of Physical Activities）的常见取值，按轻度、中等、高强度三档取近似值，并非逐项照录；力量训练的取值是 3.5、5.0、6.0。这些都是近似值，只用于粗略估算，详见《训练量与能量估算口径说明》。

## 九、迁移与一致性

- 迁移编号 0010，接在 0009 之后，建出 custom_exercises、workouts、strength_sets、cardio_entries 四张表及上述索引；回退时按相反顺序删除。
- 迁移与数据模型必须一致，由自动化测试检查：用迁移建出的库与模型对比，不应有任何差异。
- 给这四张表加上归属列的做法与前几步一致：每一张业务表都有 user_id，由统一的检查保证。
