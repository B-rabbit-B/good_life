# 步骤 05 接口清单

本文列出步骤 05 提供的全部健身接口，共 13 个，路径都以 /api/fitness 开头；另外说明步骤 04 的饮食接口因训练联动发生的行为变化。请求与响应的正文都是 JSON 格式。日期一律写成“年-月-日”的格式，例如 2026-10-07。

在线的交互式接口文档由服务自动生成，服务启动后在浏览器打开 8000 端口下的 docs 页面即可查看并直接试用，操作顺序见仓库根目录 README 的“健身模块演示”一节。

## 一、访问条件

所有健身接口都要同时满足下面的条件，由统一的入口检查，缺一不可：

1. 已登录：请求头带有效的访问令牌，否则返回 401（未登录 not_authenticated，或令牌失效 invalid_token）。
2. 已确认当前版本的免责声明：否则返回 403，错误码 disclaimer_not_accepted。
3. 健身模块对该用户开放：判断规则只有一处（步骤 01 的能力清单），本模块不重复实现。目前健身模块对所有用户开放，所以错误码 fitness_not_available（403，健身功能当前不可用）现在实际不会出现，是为将来能力清单关闭该模块预留的。

有一项自动化检查负责把关：它会逐个检查所有 /api/fitness 开头的接口，只要有一个没有挂上上述统一入口，测试就会失败。

其他约定：

- 任何接口都不接受客户端传入用户编号，请求里带了多余字段会被 422 拒绝（错误码 validation_error）。
- 别人的训练、别人的自定义动作与不存在的记录一样返回 404，不暴露是否存在。
- “今天”由服务统一提供，服务层不自行取系统日期，因此测试中可以固定为某一天。
- 所有能量消耗估算都给出区间，并带“仅为估算”的标注。

## 二、接口一览

下表不再重复说明上面三项访问条件，也不再逐个列出 validation_error（请求格式不合法时的 422）。

### 动作库

| 方法 | 路径 | 请求字段或查询参数 | 用途 | 主要错误码 |
|---|---|---|---|---|
| GET | /api/fitness/exercises/search | q（搜索词，必填，1 到 50 字） | 按名称与别名检索内置动作和本人的自定义动作，最多返回 20 个，按命中层级排序，每个结果标出命中方式 match（exact_name 名称完全相同、exact_alias 别名完全相同、prefix 以输入开头、contains 包含输入、query_contains 输入包含名称）与是不是自定义动作。返回里的 exact 表示排在第一的结果是否完全一致：完全一致时提示为空；只有名称相近的候选时 found 为真、exact 为假，提示请确认；没有命中时 found 与 exact 都为假，提示未找到、可以新增自定义动作，不会猜一个相近的动作 | 无 |
| GET | /api/fitness/exercises/custom | 无 | 列出本人的全部自定义动作（含完整字段），按名称排序 | 无 |
| GET | /api/fitness/exercises/{动作编号} | 无 | 读取一个动作的详情：名称、别名、类型、主要肌群、器械、特征、是否自定义、轻中高三档代谢当量、代谢当量的来源说明。内置动作的编号形如 ex:running，自定义动作形如 custom: 加唯一编号。力量动作的三档固定为 3.5、5.0、6.0 | exercise_not_found |
| POST | /api/fitness/exercises | name（1 到 64 字）、aliases（最多 10 个）、kind（strength 或 cardio）、primary_muscles（至少 1 个）、equipment、traits（可不填）、met_light、met_moderate、met_vigorous | 新增自定义动作，成功返回 201 和动作详情。有氧动作必须填写三档代谢当量（各大于 0、不超过 30，由轻到高不递减）；力量动作不能填 | custom_exercise_exists（409，同名）、validation_error |
| DELETE | /api/fitness/exercises/custom/{动作编号} | 无 | 删除一个自定义动作，成功返回 204，无正文。内置动作不能删除。删除后历史训练里的动作名称保留 | exercise_not_found |

### 训练记录

| 方法 | 路径 | 请求字段或查询参数 | 用途 | 主要错误码 |
|---|---|---|---|---|
| POST | /api/fitness/workouts | performed_on（训练日期，必填，不能晚于今天）；duration_minutes（整次时长，可不填）；rpe（整次主观强度 1 到 10，可不填）；note（备注，最多 500 字，可不填）；strength（力量动作列表，每项含 exercise_id 与 sets，每组含 weight_kg、reps、rest_seconds、rpe）；cardio（有氧列表，每项含 exercise_id、duration_minutes、distance_km、rpe） | 记录一次训练，成功返回 201 和这次训练（含冲突提示）。力量与有氧至少要有一项；力量动作必须是力量类型，有氧项必须是有氧类型 | workout_in_future、empty_workout、exercise_not_found、exercise_kind_mismatch |
| GET | /api/fitness/workouts | 查询参数 start、end（日期，含两端，都可不填） | 查询训练列表，日期新的在前，同一天按记录先后倒序。不填结束日期取今天，不填开始日期取结束日期往前 6 天（即最近 7 天）。开始日期晚于结束日期，或两个日期相差 366 天或以上，返回 422 | invalid_range |
| GET | /api/fitness/workouts/{训练编号} | 无 | 读取单次训练 | not_found |
| PUT | /api/fitness/workouts/{训练编号} | 同新增 | 整条替换一次训练（补录与修改都用它）：先校验新内容，通过后才删除旧的组与有氧记录再写入新的，校验失败时原记录保持不变。成功返回 200 和替换后的训练。训练里用了已删除的自定义动作时，原样提交会返回 exercise_not_found；要修改这次训练，请先把已删除的动作换成现有的动作 | not_found、workout_in_future、empty_workout、exercise_not_found、exercise_kind_mismatch |
| DELETE | /api/fitness/workouts/{训练编号} | 无 | 删除一次训练及其组与有氧记录，成功返回 204，无正文 | not_found |

训练的返回字段：编号、日期、整次时长、整次主观强度、备注、力量动作列表（动作编号、动作名称快照、顺序、每组的组序、重量、次数、休息秒数、主观强度）、有氧列表（动作编号、名称、顺序、时长、距离、主观强度）、冲突列表、创建时间、修改时间。

关于冲突列表：

- 每次训练的返回（新增、整条替换、读取单条、列表里的每一项）都带冲突列表，用今天生效的运动限制类医嘱判断。没有运动限制医嘱、或没有冲突时为空列表。
- 冲突只提示，从不阻止保存：有冲突时新增、替换照样成功。
- 每一条冲突含医嘱条目编号、医嘱内容、涉及的说法、级别（conflict 冲突，unverifiable 无法判断）、提示文字、涉及的训练编号列表。规则与词汇表见《训练信号与饮食联动说明》。

### 汇总、趋势与信号

| 方法 | 路径 | 请求字段或查询参数 | 用途 | 主要错误码 |
|---|---|---|---|---|
| GET | /api/fitness/summary/week | 查询参数 start（一周的开始日期，必须是星期一，可不填，不填取今天所在这一周的星期一） | 周汇总：训练次数、训练天数、总训练量、各肌群训练量、有氧分钟数、能量消耗区间（下限与上限，千卡）、估算状态（ok 或 missing_body_weight）、说明（含“仅为估算”）。档案没有体重时区间为空、状态为 missing_body_weight | invalid_week_start |
| GET | /api/fitness/exercises/{动作编号}/trend | 无 | 单个动作的重量进步趋势：按日期从早到晚的点，每个点含日期、最高重量、训练量、总次数、组数；没有记录时点列表为空。已删除的自定义动作只要用户的训练里用过，仍然可以查询 | exercise_not_found |
| GET | /api/fitness/signal | 无 | 今日训练信号：今天是否训练、训练类型、最高强度档、估算消耗区间、估算状态、涉及肌群、训练条数、冲突、说明、免责标注。字段含义见《训练信号与饮食联动说明》 | 无 |

信号的固定取值：强度 intensity 是 none、light、moderate、vigorous 之一；估算状态 energy_status 是 ok、missing_body_weight、no_training 之一；训练类型 kinds 里是 cardio、strength 之一或两者（按名称顺序）。

## 三、对饮食接口的影响

健身模块开放后，步骤 04 的饮食接口有下面的变化，接口本身和请求字段都没有改：

| 接口 | 变化 |
|---|---|
| GET /api/nutrition/summary | 查询哪一天，就把哪一天训练估算消耗的下限加进当天的能量需求（目标、范围上下限），剩余额度随之变化；需求的说明里多一句“已计入当天训练估算消耗的下限 N 千卡。”。休息日、无法估算需求、没有体重、查询今天以后的日期时不加。计入时只读训练记录，不读医嘱，查询任何日期都不会改变医嘱状态 |
| GET /api/nutrition/needs | 按今天计算，加上今天的训练消耗下限，规则同上，同样不读医嘱 |
| POST /api/nutrition/evaluate 与 /evaluate-meal | 返回的依据来源多了 training（训练）：训练日按训练规则给推荐依据，计入训练消耗时每次判断带一条说明依据，运动限制冲突以信息依据出现；休息日与步骤 04 完全一致。依据的类别名新增 training_rule、training_energy_bonus、training_conflict、training_unverifiable。详见《训练信号与饮食联动说明》与步骤 04 的《约束融合规则说明》 |

## 四、错误码汇总

| 错误码 | 状态码 | 含义 | 出现在 |
|---|---|---|---|
| not_authenticated | 401 | 未登录 | 全部接口 |
| invalid_token | 401 | 令牌失效 | 全部接口 |
| disclaimer_not_accepted | 403 | 未确认当前版本的免责声明 | 全部接口 |
| fitness_not_available | 403 | 健身功能当前不可用（预留，目前不会出现） | 全部接口 |
| validation_error | 422 | 请求格式不合法、字段多余、取值超出范围、有氧动作缺代谢当量、力量动作填了代谢当量等 | 全部接口 |
| exercise_not_found | 404 | 动作不存在，或是别人的自定义动作，或内置动作被当作自定义动作删除 | 动作详情、删除自定义动作、新增与替换训练、趋势 |
| custom_exercise_exists | 409 | 已经有同名的自定义动作 | 新增自定义动作 |
| not_found | 404 | 训练不存在，或不属于当前用户 | 读取、替换、删除训练 |
| workout_in_future | 422 | 训练日期晚于今天 | 新增、替换训练 |
| empty_workout | 422 | 没有记录任何力量动作或有氧项目 | 新增、替换训练 |
| exercise_kind_mismatch | 422 | 动作类型与记录位置不符，例如把有氧动作记在力量训练里 | 新增、替换训练 |
| invalid_range | 422 | 查询训练列表的日期范围不合法：开始晚于结束，或相差 366 天或以上 | 训练列表 |
| invalid_week_start | 422 | 周汇总的开始日期不是星期一 | 周汇总 |

检索没有结果不是错误，返回 200，found 为假；只有名称相近的候选也不是错误，返回 200，found 为真、exact 为假。
