# 步骤 05 训练信号与饮食联动说明

本文说明健身模块怎样把“今天练了什么”变成一份信号，约束引擎怎样使用这份信号，训练消耗怎样计入当天的能量额度，运动限制类医嘱怎样与训练做冲突检测，并用休息日与训练日的对比示例说明“联动”到底改变了什么。本文描述的是实际代码的行为。

## 一、分工：健身模块只给信号，引擎给结论

- 健身模块只描述事实：今天是否训练、练了哪类、强度大致水平、估算消耗区间、涉及哪些肌群、与医嘱运动限制有没有冲突。它不给任何饮食结论。
- 饮食结论只由约束引擎（步骤 04）统一给出，保持单一出口。引擎并不直接依赖健身模块：由“上下文组装”一步读出训练信号，转成引擎自己的简化结构后交给它。
- 是否读取训练信号，由统一的能力清单决定（目前健身模块对所有用户开放）；如果将来能力清单对某个用户关闭了健身模块，引擎与需求估算都不会去读训练，行为与步骤 04 完全一致。
- 同样的输入永远得到同样的输出，信号里的列表都按固定规则排序。

## 二、今日训练信号

信号只针对“今天”，由服务统一提供今天的日期，请求里不能传日期。字段如下。

| 字段 | 含义 |
|---|---|
| day | 信号对应的日期，即今天 |
| trained | 今天是否有训练记录 |
| kinds | 训练类型列表，可能有 cardio（有氧）、strength（力量），按名称顺序排列；休息日为空 |
| intensity | 今天最高的强度档：none（休息日）、light、moderate、vigorous；一天有多次训练时取最高 |
| energy_low、energy_high | 今天所有训练估算消耗区间之和（千卡）；休息日或缺体重时为空 |
| energy_status | ok（有估算）、missing_body_weight（今天练了但档案没有体重）、no_training（休息日） |
| muscles | 涉及的肌群：今天所有力量动作的主要肌群，去重后按名称排序；有氧动作不计入 |
| workout_count | 今天的训练条数 |
| conflicts | 今天的训练与医嘱运动限制的冲突提示，见第五节 |
| notes | 估算的说明，例如缺体重时说明需要体重、已删除的自定义动作说明 |
| disclaimer | “能量消耗仅为估算”的标注 |

强度档的分档、估算公式与区间见《训练量与能量估算口径说明》。

## 三、训练消耗怎样计入当天能量额度

### 规则

- 有训练的日子，把今天训练估算消耗区间的“下限”加到当天的能量需求里：能量目标、能量范围的下限、能量范围的上限三个数都加上同一个数。
- 蛋白质、脂肪、碳水化合物、膳食纤维、钠的目标不变，只加能量。
- 需要加的数取整后使用，并在需求的说明里追加一句“已计入当天训练估算消耗的下限 N 千卡。”
- 下面几种情况不加：休息日；档案缺少估算每日需求所需的信息，无法估算需求；今天练了但档案没有体重，估算不出消耗。

### 哪些接口受影响

- 每日汇总：查询哪一天，就加上哪一天的训练消耗下限，所以查询过去某天时，用的是那天的训练；汇总里的剩余额度也随之变化。查询今天以后的日期时不加（那天不可能有训练记录），直接给按档案估算的需求。
- 需求估算接口：按今天计算，加上今天的训练消耗下限。
- 两个判断接口（单个食物与一整餐）：按今天计算，规则同上。三者对同一天给出同样的能量需求。
- 年龄始终按今年计算，不随查询的日期变化。
- 计入额度时只读训练记录与档案里的体重，不读医嘱，所以查看任何一天的汇总或需求都不会改变医嘱的状态。与医嘱的冲突只在今日训练信号、两个判断接口和训练记录的返回里出现，都按今天生效的医嘱计算。

### 为什么这样定

- 加下限而不是估算值，是用户选定的偏保守做法：估算本身误差大，只把“比较有把握已经消耗掉的部分”算作可以多吃的额度，避免因为估算偏高而鼓励多吃。
- 目标、下限、上限一起加，保持区间的相对宽度不变，也让“超过上限”的判断随训练日同步放宽。
- 蛋白质等不跟着加，是因为本步骤没有依据能把训练消耗换算成这些营养素的额度，宁可保持原样。
- 加了多少一定写明（需求说明里、每条判断的信息依据里、超限提示里），不做悄悄的调整。

## 四、引擎的训练来源规则

引擎的依据来源在步骤 04 的医嘱、经期提示、健身目标、当日摄入、个人偏好之外，新增“训练”，排序位置在健身目标之后、当日摄入之前，固定顺序为：医嘱、经期提示、健身目标、训练、当日摄入、个人偏好。训练是软约束：只会给出“推荐”或“信息”，不会单独得出“不建议”。

### 训练推荐规则

| 条件 | 涉及的食物标签 | 作用 | 提示内容 |
|---|---|---|---|
| 今天有力量训练 | 高蛋白 | 推荐 | 力量训练日保证优质蛋白，有助于肌肉恢复 |
| 今天最高强度为中等或高强度（力量或有氧都算） | 快消化碳水 | 推荐 | 训练日可以在训练前后适当安排快碳，帮助补充糖原 |

- 休息日不产生任何训练依据。
- 只有轻度的有氧训练日（整次与各条目都明确填了轻度，没填主观强度的按中等算），不满足任何一条，也不产生推荐依据。
- 依据的文字固定写成：“训练提示（今天有力量训练，强度中等）：提示内容（这个食物：命中的标签名）。”，今天既有力量又有有氧时写“力量训练、有氧训练”。依据的引用是 strength 或 intensity_moderate_or_above。
- 规则放在软规则数据文件里，启动时校验标签必须存在。

### 说明性的信息依据

- 能量额度说明：训练日并且确实把训练消耗加进了需求时，每一次判断都带一条训练信息依据：“今天的能量额度已计入训练估算消耗的下限 N 千卡。”引用是 needs。没有计入（休息日、需求无法估算、缺体重）就没有这条。
- 超限提示：当天摄入加上这一份后超过估算的每日能量上限时，提示里在上限后面补一句“（已计入训练估算消耗的下限 N 千卡）”，让用户知道上限已经放宽过。
- 冲突提示：见第五节，以训练来源的信息依据出现。

### 不会冲淡硬约束与谨慎

- 训练的推荐依据不改变结论：医嘱的不建议依据仍然使结论为不建议，医嘱无法判断、各类谨慎仍然使结论为谨慎。例如训练日吃医嘱忌口的猪肝，仍然是不建议，权衡说明写明医嘱优先，同时承认有训练方面的好处。
- 训练的推荐依据与别的来源的谨慎并存时，权衡说明列出“有利的来自……，需要注意的来自……”，请用户结合情况权衡，结论仍是谨慎。例如减脂用户吃一个同时带有甜食和快消化碳水标签的食物，训练日有“快碳”的推荐，但减脂目标对甜食的谨慎依据仍在，结论是谨慎。
- 当日摄入超限的谨慎也不会被训练的推荐抵消。

## 五、运动限制类医嘱的冲突检测

### 检测哪些医嘱

只检测“运动限制”类的医嘱，范围是医嘱条目当前生效或待复核的（待复核的仍按原要求执行，冲突提示里会注明“这条医嘱正在待复核”）。判断用的是今天的当前约束。冲突只提示，从不阻止保存训练。

训练记录的每个返回（新增、整条替换、读取单条、列表里的每一项）都带“冲突”列表，针对这一条训练，按今天生效的医嘱计算；今日训练信号里的冲突针对今天全部训练。整条替换后冲突会重新计算。

### 两种级别

- 冲突（conflict）：训练明确触及医嘱里的说法。提示写：“这次训练可能与医嘱「医嘱内容」冲突：涉及「说法」，请确认是否适合继续，或咨询医生。”
- 无法判断（unverifiable）：程序没法确定。提示写：“无法自动判断这次训练是否符合医嘱「医嘱内容」中的「说法」，请自行核对”，能说出原因时在后面写“（原因：……）”。

同一条医嘱、同一个说法，可以同时给出冲突和无法判断两条（例如两次训练，一次冲突、一次无法判断）；每一条带上涉及的训练编号列表。结果按医嘱编号、说法、级别排序，与输入顺序无关。

### 词汇表

医嘱里每个“涉及对象”（例如“提重物”“剧烈运动”）去掉空白后，先原样在词汇表里查，查不到时去掉结尾的“运动”“活动”“动作”再查一次（例如“跑步运动”按“跑步”判断）。词汇表共 26 个说法，分为下面几种：

| 说法 | 判断规则 |
|---|---|
| 运动、锻炼、健身、体育锻炼 | 任何一次训练都算冲突 |
| 剧烈运动、剧烈活动、高强度运动、高强度训练、剧烈 | 当天最高强度档达到高强度，或训练里有带“高冲击”特征的动作（例如跳绳、波比跳），算冲突 |
| 提重物、重物、举重、搬重物 | 力量训练里有任何一组重量大于 0，算冲突 |
| 负重 | 同样是有一组重量大于 0 算冲突；否则一律无法判断，因为“负重”也可能指患肢负重，跑步、跳跃、深蹲等也会负重，程序无法区分 |
| 跑步、跑、长跑 | 训练里有带“跑步”特征的动作，算冲突 |
| 游泳 | 带“游泳”特征，算冲突 |
| 弯腰 | 带“弯腰”特征（例如硬拉、杠铃划船），算冲突 |
| 跳跃、跳 | 带“跳跃”特征，算冲突 |
| 骑车、骑行 | 带“骑行”特征，算冲突 |
| 卧床 | 只要有训练，一律无法判断，原因是“卧床可能指需要卧床休息”，请自行核对能否训练 |
| 久坐、久站 | 不适用，与训练无关，不产生任何提示 |

词汇表里没有的说法（例如“避免推拉动作”），只要当天有训练，一律给“无法判断，请自行核对”。没有训练记录时不产生任何提示。

### 无法判断的具体情形

除了词汇表里没有的说法，下面这些情形也给“无法判断”，并在原因里写明：

- 高强度限制：这次训练没有达到高强度、也没有高冲击动作，但整次训练没有填主观强度，并且有任何一组力量或任何一项有氧没有填主观强度，这部分的实际强度不详，原因是“未填写主观强度”（只要整次填了，没填的组与有氧项按整次的强度算，不再提示；其他组填了也不能代替没填的那部分）；
- 提重物、负重类限制：没有任何一组有重量，但有重量器械的动作里有重量为 0 的组，多半是没填重量，原因是“未填写重量”（自重动作与无器械动作的 0 千克是正常的，不算）；
- 负重：见上表，原因是“负重可能指患肢负重（跑步、跳跃、深蹲等也会负重）”；
- 卧床：见上表，原因是“卧床可能指需要卧床休息”；
- 动作特征类限制（跑步、游泳、弯腰、跳跃、骑行）与高强度限制：训练里有自定义动作（包括已删除的自定义动作），而它没有标注所问的特征，程序无法确定，原因是“自定义动作「名称」未标注相关特征”。

多个原因去重后排序再写出，所以提示文字是确定的。

### 对饮食判断的影响

训练与医嘱的冲突提示会作为“训练来源的信息依据”出现在饮食判断里，写法是冲突提示加“饮食判断不受影响，请留意运动安排。”它引用的是那条医嘱的编号，不改变饮食结论。

## 六、休息日与训练日的对比示例

以下示例用同一个用户：男性，增肌目标，体重 70 千克，档案其余信息完整，年龄 36 岁，活动水平中度。按步骤 04 的公式，休息日的每日能量需求是 2760 千卡，范围 2484 至 3036 千卡。

训练日：今天记录了一次 60 分钟的力量训练，主观强度 7（中等），估算 350 千卡，区间 280 至 420 千卡。

| 比较项 | 休息日 | 训练日 |
|---|---|---|
| 训练信号 | 没训练，强度 none，估算状态 no_training | 训练，类型力量，强度 moderate，区间 280 至 420，状态 ok |
| 每日能量需求 | 2760，范围 2484 至 3036 | 3040，范围 2764 至 3316；需求说明多一句“已计入当天训练估算消耗的下限 280 千卡。” |
| 判断米饭 200 克（232 千卡） | 没有任何训练依据 | 训练推荐：训练日可以安排快碳；训练信息：能量额度已计入下限 280 千卡 |
| 判断鸡胸肉 150 克 | 只有增肌目标的推荐（高蛋白） | 增加训练推荐：力量训练日保证优质蛋白；训练信息：能量额度已计入下限 280 千卡 |
| 今天已吃 2900 千卡，再判断米饭 200 克，合计 3132 千卡 | 超过上限 3036，谨慎，提示当日摄入超限 | 上限 3316，没有超限，不再因能量谨慎，结论适合 |
| 再吃更多，米饭 400 克（464 千卡），合计 3364 千卡 | 谨慎 | 仍超过训练日上限 3316，谨慎，提示里写“已计入训练估算消耗的下限 280 千卡”；训练的推荐依据不会抵消这条谨慎 |

对应的自动化测试见《验收记录》的第 4 条。

## 七、已知局限

- 训练消耗只计入能量，蛋白质、碳水等不随训练调整；
- 训练推荐只有两条规则，不区分训练前后、也不给具体份量；
- 训练信号只看今天；每日汇总可以回看某天，但判断接口只判断今天；
- 冲突检测依赖词汇表与动作的特征标注，词汇表没有的说法一律“无法判断”，需要用户自行核对；自定义动作的特征由用户自己标注，没标注就无法判断；
- 无法判断的情形是宁可提示也不漏报，可能偶尔多提示。
