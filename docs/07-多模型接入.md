# 步骤 07：多模型接入

## 目标

让用户填写模型服务的地址和密钥后，点击"获取模型"就能看到可用模型列表并选择；后端用统一方式调用不同厂商的模型，并知道每个模型是否支持看图与调用工具。

## 范围

- 模型服务配置：用户可以添加多个服务，每个包含名称、服务类型、地址、密钥。
- 获取模型：点击后由后端向对应服务拉取模型列表，返回名称与基础信息。
- 能力标注：为每个模型标注是否支持看图、是否支持调用工具、是否为对话类模型。拉取到的列表本身通常不含这些信息，因此要维护一份能力对照表，并允许用户手动修正。
- 连通性测试：用户保存前可以发起一次测试，确认地址、密钥、模型可用。
- 模型选择：用户可以为不同用途选择不同模型，至少区分"日常对话"和"看图识别"两类用途。
- 服务类型覆盖：大多数国内外服务使用统一的兼容格式，少数服务格式不同，需要单独适配，比如 Claude、Gemini。
- 统一调用：后端对外只暴露一种调用方式，内部适配各厂商。
- 密钥保护：密钥加密存储，前端只显示掩码，不回传明文。
- 用量与失败处理：调用失败时给出可读的原因，如密钥错误、额度不足、模型不存在、网络超时。

## 明确不做

- 自建模型中转站、计费与额度分发。
- 模型微调与本地部署模型。
- 拍照识别的具体流程，放到步骤 09。

步骤 01。

## 关键设计

- 由后端统一去拉取模型列表，浏览器不直接带着用户密钥请求第三方，一方面避免跨域问题，另一方面避免密钥暴露。
- 采用 LiteLLM 的 Python 库作为统一适配层，它已经提供拉取模型列表与判断模型能力的功能；如实际测试发现覆盖不足，可对个别服务单独补适配。
- 针对格式特殊的服务，按类型分别处理拉取与解析，思路参考 Cherry Studio 的按厂商分策略设计，只借鉴思路，不拷贝代码。
- 设置页的交互参考 LobeHub 的模型列表页，只借鉴交互思路，不拷贝代码。
- 能力对照表来源清晰、可更新，并支持用户手动覆盖。
- 密钥使用方式：调用时才解密，解密后不写日志。

## 交付物

- 模型服务配置与能力对照表的数据说明。
- 支持的服务类型清单，以及各类型的拉取与调用方式说明。
- 接口清单（添加服务、获取模型、连通性测试、选择用途模型、统一调用入口）。
- 国内外主流服务的实测记录：至少覆盖通义、DeepSeek、豆包、智谱、Claude 与一个兼容格式的通用服务。

## 验收标准

1. 填入一个服务的地址和密钥，点击获取模型，能列出可用模型。
2. 至少四家不同服务实测通过，实测记录中写明各家拉取与调用的实际表现，包括调研中未能核实的情况。
3. 每个模型的看图与工具调用标注基本正确，错误的可以手动修正。
4. 连通性测试能区分密钥错误、地址错误、模型不可用等原因。
5. 密钥在数据库中是密文，接口与前端永远不回传明文。
6. 可以为"对话"与"看图识别"分别选择不同模型，并生效。
7. 用不支持看图的模型做看图用途时，系统给出明确提示，而不是静默失败。

## 开源参考与许可证注意

- LiteLLM：MIT 许可，可嵌入使用。
- LobeHub 与 Cherry Studio：许可证有限制或强传染，只参考交互与设计思路，不拷贝代码。
- 新型中转类项目：强传染或运营型定位，不作为嵌入方案。

## 风险与对策

- 风险：不同服务的模型列表格式不一致。对策：按类型分别适配，并做实测。
- 风险：调研中提到国内各家的模型列表接口行为未逐家验证。对策：本步骤验收要求逐家实测并留档。
- 风险：模型能力标注不准。对策：允许手动修正，并在拍照识别等关键功能前做能力检查。
- 风险：用户密钥泄露。对策：加密、掩码、不入日志。
