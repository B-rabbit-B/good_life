# 步骤 04 接口清单

本文列出步骤 04 提供的全部饮食接口，共 11 个。所有接口路径都以 /api/nutrition 开头。请求与响应的正文都是 JSON 格式。日期一律写成“年-月-日”的格式，例如 2026-10-06。

在线的交互式接口文档由服务自动生成，服务启动后在浏览器打开 8000 端口下的 docs 页面即可查看并直接试用，操作顺序见仓库根目录 README 的“饮食与约束引擎演示”一节。

## 一、访问条件

所有饮食接口都要同时满足下面的条件，由统一的入口检查，缺一不可：

1. 已登录：请求头带有效的访问令牌，否则返回 401（未登录 not_authenticated，或令牌失效 invalid_token）。
2. 已确认当前版本的免责声明：否则返回 403，错误码 disclaimer_not_accepted。
3. 饮食模块对该用户开放：判断规则只有一处（步骤 01 的能力清单），本模块不重复实现。目前饮食模块对所有用户开放，所以错误码 nutrition_not_available（403，饮食功能当前不可用）现在实际不会出现，它是为将来能力清单关闭该模块预留的。

有一项自动化检查负责把关：它会逐个检查所有 /api/nutrition 开头的接口，只要有一个没有挂上上述统一入口，测试就会失败。

其他约定：

- 任何接口都不接受客户端传入用户编号，请求里带了多余字段会被 422 拒绝（错误码 validation_error）。
- 统一的错误格式：错误码加中文提示。别人的饮食记录与不存在的记录一样返回 404，错误码 not_found，不暴露记录是否存在。
- “今天”由服务统一提供，服务层不自行取系统日期，因此测试中可以固定为某一天。
- 所有判断类接口的返回都带免责说明；汇总与需求类接口的返回都带“估算，仅供参考”的提示。

## 二、接口一览

下表不再重复说明上面三项访问条件，也不再逐个列出 validation_error（请求格式不合法时的 422）。

### 营养库查询

| 方法 | 路径 | 请求字段或查询参数 | 用途 | 主要错误码 |
|---|---|---|---|---|
| GET | /api/nutrition/foods/search | q（搜索词，必填，1 到 50 字） | 按名称、别名、常用名、基本名称检索食物，最多返回 20 个，按命中层级排序，每个结果标出命中方式 match（exact_name 名称完全相同、common_name 常用名对照表里的叫法完全相同、exact_alias 别名完全相同、prefix 名称以输入开头、contains 名称包含输入、query_contains 输入包含名称；常用名与名称完全相同排在同一层级，例如搜“西红柿”命中番茄，命中方式是 common_name）。返回里的 exact 表示排在第一的结果是否完全一致（命中方式为 exact_name、common_name 或 exact_alias）：完全一致时提示为空；只有名称相近的候选时 found 仍为真、exact 为假，并提示“没有完全一致的食物，下面是名称相近的候选，请确认是否是你要找的”，例如搜“酸菜鱼”只得到酸白菜；没有任何命中时 found 与 exact 都为假、结果为空，并带明确的“未找到”提示，不会猜一个相近的食物 | 无 |
| GET | /api/nutrition/foods/{食物编号} | 无 | 读取一个食物的详情：每 100 克的八项营养、标签（营养学与传统经验分类标出）、份量换算、默认克数、来源（数据集、编号、授权状态、说明） | food_not_found |
| GET | /api/nutrition/tags | 无 | 读取全部 42 个标签的定义：编号、中文名、类别、依据、审核状态 | 无 |

### 饮食记录

| 方法 | 路径 | 请求字段或查询参数 | 用途 | 主要错误码 |
|---|---|---|---|---|
| POST | /api/nutrition/meals | eaten_on（吃的日期，必填，不能晚于今天）；meal_type（早餐 breakfast、午餐 lunch、晚餐 dinner、加餐 snack）；food_id（必填）；grams（克数）与 portion（份量，含单位 unit 与份数 count）二选一，必须填一项；note（备注，可不填，最多 200 字） | 记录一餐里的一个食物，成功返回 201 和这条记录（含记录时按克数算出的营养快照） | meal_in_future、food_not_found、invalid_portion |
| GET | /api/nutrition/meals | 查询参数 date（日期，可不填，不填按今天） | 读取某一天的全部记录，按早餐、午餐、晚餐、加餐的顺序，同一餐内按记录时间排列 | 无 |
| PATCH | /api/nutrition/meals/{记录编号} | eaten_on、meal_type、food_id、grams、portion、note，均可选，只提交要改的；前三项不能提交为空 | 修改一条记录。只有提交了 food_id、grams 或 portion 之一，营养快照才按当前营养库重新计算；只改备注、餐别或吃的日期时，保留原来的营养快照，也不会再去查营养库；吃的日期仍不能晚于今天 | not_found、meal_in_future、food_not_found、invalid_portion |
| DELETE | /api/nutrition/meals/{记录编号} | 无 | 删除一条记录，成功返回 204，无正文 | not_found |
| GET | /api/nutrition/summary | 查询参数 date（日期，可不填，不填按今天） | 某一天的每日汇总：每一餐与全天的能量和营养素合计、数据不完整的营养素、估算的需求、剩余额度（需求减去已摄入，只有能量、蛋白质、钠三项；档案不完整时为空）、估算提示 | 无 |
| GET | /api/nutrition/needs | 无 | 按档案估算每日需求：能量与范围、蛋白质、脂肪与碳水化合物的范围、膳食纤维、钠上限。档案缺出生年份、身高、体重、活动水平任一项时，状态为信息不足并列出缺少的项，不给数值 | 无 |

说明：

- 克数需要大于 0 且不超过 5000；份数需要大于 0 且不超过 20；份量单位必须是这个食物有的单位（食物详情里列出），否则返回 invalid_portion，并在提示里列出可选单位。
- 记录里存放的是记录当时算出的营养快照，之后营养库更新不会改变历史汇总；汇总完全按快照相加，所以每日汇总与手算一致。营养数据缺失的项在记录里保持空值，汇总从零开始累加，缺失的项按 0 计入，所以汇总里的合计都是数字，“数据不完整的营养素”会列出哪些项有缺失、合计可能偏低。只改备注、餐别或日期的修改不会重算快照。
- 备注加密保存，其余字段（日期、餐别、食物、克数、营养快照）明文保存，因为汇总要按日期与数值查询。
- 汇总里的估算需求按今天的日期与档案计算（年龄按今年算），不随查询的日期变化。

### 饮食判断

| 方法 | 路径 | 请求字段 | 用途 | 主要错误码 |
|---|---|---|---|---|
| POST | /api/nutrition/evaluate | food_id（必填）；grams 或 portion（最多填一项，都不填按食物的默认份量） | 判断一个食物对当前用户是否适合：结论（适合 suitable、谨慎 caution、不建议 not_recommended）、逐条依据、权衡说明、数据来源、免责说明，以及这一份的营养 | food_not_found、invalid_portion |
| POST | /api/nutrition/evaluate-meal | items（1 到 20 项，每项同上） | 判断一整餐：逐项给出结论与依据，后面的食物计入前面食物的份量，整餐结论取最严重的一个，并给出整餐营养合计 | food_not_found、invalid_portion |

判断返回的每条依据包括：来源 source、作用 effect、类别名 code、说明文字 message、引用 ref（医嘱条目编号、经期提示编号、目标的取值 lose_fat 或 gain_muscle、营养素名称 energy_kcal 或 sodium_mg、档案不完整时的 needs，或档案里的说法）。结论、来源、作用与检索的命中方式都只会是下面列出的固定取值之一，接口文档里也按固定取值列出；类别名是普通文字，目前的全部取值见下表。规则细节见《约束融合规则说明》。

| 字段 | 固定取值 |
|---|---|
| 结论 conclusion（单个食物与整餐） | suitable 适合、caution 谨慎、not_recommended 不建议 |
| 来源 source | medical 医嘱、cycle 经期提示、goal 健身目标、intake 当日摄入、preference 个人偏好 |
| 作用 effect | block 不建议依据、unverifiable 无法判断、caution 谨慎、prefer 推荐、info 信息 |
| 检索命中方式 match | exact_name、common_name、exact_alias、prefix、contains、query_contains |

| 类别名 code | 来源 | 作用 | 含义 |
|---|---|---|---|
| avoid_match | 医嘱 | 不建议依据 | 食物本身或菜品配方里的食材命中忌口类说法 |
| avoid_unverifiable | 医嘱 | 无法判断 | 饮食禁忌或用药相关饮食注意里的说法程序对不上，无法判断这个食物是否属于它 |
| require_violated | 医嘱 | 不建议依据 | 食物带有要求类说法的“违反”标签 |
| require_caution | 医嘱 | 谨慎 | 食物带有要求类说法的“需控制量”标签，例如糖尿病饮食下的快消化碳水 |
| require_met | 医嘱 | 推荐 | 食物带有要求类说法的“符合”标签 |
| require_unverifiable | 医嘱 | 无法判断 | 饮食要求类医嘱里的说法程序对不上，无法判断这个食物是否符合它 |
| cycle_rule | 经期提示 | 谨慎或推荐 | 命中当前经期阶段的一条提示规则 |
| goal_rule | 健身目标 | 谨慎或推荐 | 命中健身目标的一条规则 |
| energy_over_limit | 当日摄入 | 谨慎 | 加上这一份后能量超过估算的每日上限 |
| sodium_over_limit | 当日摄入 | 谨慎 | 加上这一份后钠超过每日建议上限 |
| needs_unknown | 当日摄入 | 信息 | 档案不完整，无法估算今天的剩余额度 |
| avoidance_match | 个人偏好 | 谨慎 | 命中档案里填写的不吃的食物 |
| preference_violated | 个人偏好 | 谨慎 | 带有档案饮食偏好的“违反”或“需控制量”标签 |
| preference_met | 个人偏好 | 推荐 | 带有档案饮食偏好的“符合”标签 |

## 三、为什么判断只针对今天

两个判断接口没有日期参数，请求里带 date 字段会被 422 拒绝。原因：

- 引擎读取医嘱“当前约束”时，系统会按传入的日期刷新医嘱状态（生效中的条目到期转待复核，过期的待确认条目转已作废）。如果判断可以指定未来的日期，一次“试算”就会提前改变用户真实的医嘱数据；
- 判断过去的日期也取不到当时的医嘱状态与阶段，结果没有意义；
- 所以日期只由服务端提供，并且只取今天。饮食记录与汇总是只读查询，可以指定日期查看历史。

## 四、错误码汇总

| 错误码 | 状态码 | 含义 | 出现在 |
|---|---|---|---|
| not_authenticated | 401 | 未登录 | 全部接口 |
| invalid_token | 401 | 令牌失效 | 全部接口 |
| disclaimer_not_accepted | 403 | 未确认当前版本的免责声明 | 全部接口 |
| nutrition_not_available | 403 | 饮食功能当前不可用（预留，目前不会出现） | 全部接口 |
| validation_error | 422 | 请求格式不合法、字段多余、克数与份量同时填写（判断类接口）等 | 全部接口 |
| food_not_found | 404 | 营养库里没有这个食物编号 | 食物详情、记录、修改记录、判断 |
| not_found | 404 | 记录不存在，或不属于当前用户 | 修改、删除饮食记录 |
| invalid_portion | 422 | 克数与份量没有填其中一项（或同时填了，记录接口）；克数、份数超出范围；份量单位不存在 | 记录、修改记录、判断 |
| meal_in_future | 422 | 吃的日期晚于今天 | 记录、修改记录 |

检索没有结果不是错误，返回 200，found 为假；只有名称相近的候选也不是错误，返回 200，found 为真、exact 为假。
