# 步骤 02 经期数据表说明

本文说明步骤 02 新增的三张数据表。表结构由数据库迁移脚本统一管理（迁移编号 0005，接在步骤 01 的最后一个迁移之后），按顺序执行即可在空库中建出全部表。

阅读约定与步骤 01《数据表说明》一致：

- “是否必填”指数据库层面该列能否为空。
- “是否加密”指该列存入数据库时是否已被加密，加密后在数据库里只能看到密文，需要持有加密密钥才能还原。
- 所有时间列都带时区；日期列只有年月日，没有时区。

## 一、cycle_periods（月经记录）

每一行是一次月经，记录开始日和结束日。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 记录唯一标识 | 是（主键） | 否 | 随机生成的唯一编号（UUID） |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引；用户被删除时，其月经记录一并删除 |
| start_date | 月经开始日 | 是 | 否 | 日期；不能晚于“今天” |
| end_date | 月经结束日 | 否 | 否 | 日期；为空表示这次月经还没有结束（正在进行中）；填写时不能早于开始日，不能晚于“今天”，与开始日相距最多 14 天（即一次经期最长 15 天） |
| created_at | 记录创建时间 | 是 | 否 | 创建时由数据库自动填写 |

补充说明：

- 同一个用户同一个开始日只能有一条记录（数据库设有唯一约束，约束名为 uq_cycle_periods_user_start）。
- 同一个用户的两次经期日期范围不能重叠；结束日为空的记录按“一直持续到今天”参与重叠判断。这一条由服务在写入前检查，数据库唯一约束只负责开始日不重复。
- 一次尚未结束的经期，开始日距今天超过 14 天时不能新建或保存，需要先补上结束日期。

## 二、cycle_day_logs（每日记录）

每一行是某一天的身体情况记录，一天最多一条，重复提交同一天会整条替换。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 记录唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引；用户被删除时一并删除 |
| log_date | 记录所属日期 | 是 | 否 | 日期；不能晚于“今天” |
| details | 当天的全部内容 | 是 | 是 | 整体加密。解密后包含五项：流量、疼痛程度、情绪、症状、备注，取值见下表 |
| updated_at | 最近修改时间 | 是 | 否 | 创建时取数据库当前时间，每次修改由数据库一并更新 |

同一个用户同一天只能有一条记录（唯一约束名为 uq_cycle_day_logs_user_date）。

details 解密后各项内容的取值：

| 项 | 含义 | 可以为空 | 取值说明 |
|---|---|---|---|
| flow | 流量 | 是 | none（无）、spotting（点滴）、light（少）、medium（中）、heavy（多）五选一 |
| pain | 痛经程度 | 是 | 整数 0 到 3，0 表示不痛，3 表示最痛 |
| mood | 情绪 | 是 | good（好）、normal（平稳）、low（低落）、irritable（烦躁）、anxious（焦虑）五选一 |
| symptoms | 其他症状 | 否 | 文字标签列表，最多 20 个，每个 1 到 32 个字符（首尾空白会被去掉）；不填时是空列表 |
| note | 备注 | 是 | 自由文本，最长 500 个字符 |

## 三、cycle_settings（经期设置）

每个用户最多一行，第一次读取经期设置时自动创建，默认是“正常记录”。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| user_id | 归属用户，同时是主键 | 是 | 否 | 指向 users 的 id，一个用户只能有一行；用户被删除时一并删除 |
| status | 当前状态 | 是 | 否 | tracking（正常记录，默认）、pregnant（孕期）、paused（暂停预测）三选一；后两种状态下不再输出经期预测，阶段显示为未知，阶段提示里只保留通用提示 |
| updated_at | 最近修改时间 | 是 | 否 | 创建时取数据库当前时间，每次修改由数据库一并更新 |

补充说明：

- 并发的首次请求同时创建设置行时，数据库主键冲突的一方什么也不做，随后重新读取，因此不会出现重复行或报错。
- 切换状态不会删除任何已记录的经期数据，恢复为“正常记录”后预测立即恢复。

## 四、为什么日期明文、每日记录加密

- 预测和阶段判断需要按日期排序、范围查询，还要判断两次经期是否重叠、同一天是否已有记录。如果日期也加密，这些查询就只能把全部数据取回后逐条解密再处理，既慢也让数据库唯一约束无法生效。所以经期的开始日、结束日和每日记录的日期明文存放，用于排序、查询和约束。
- 每日记录里的流量、疼痛、情绪、症状、备注才是最私密的身体细节，预测并不需要在数据库里对它们做查询，所以整体加密：数据库里看到的只是一串密文，没有加密密钥无法还原。统计症状规律时，由服务把最近一年的记录取出后在内存中解密再汇总。
- 也就是说，单看数据库能推断出“这个用户大致的经期日期”，但推断不出任何具体的症状、疼痛或备注内容。
- 加密使用的密钥与步骤 01 相同（配置项 FIELD_ENCRYPTION_KEY），该密钥丢失或更换后，已加密的每日记录将无法解密。

## 五、归属约定

延续步骤 01 的约定，并在本步骤全部落实：

- 三张表都有 user_id 列，指明这行数据属于哪个用户（经期设置表以 user_id 作主键）。
- 月经记录、每日记录、经期设置的所有查询都从统一的“只查当前用户”入口发起；按编号读取、修改、删除某次月经时，统一使用“按编号取当前用户的一条记录，取不到就返回未找到”的入口。
- 别人的月经记录与不存在的月经记录一样返回 404（错误码 not_found），不暴露该编号是否存在。
- 所有经期接口都不接受客户端传入的用户编号，请求里带了多余字段会被 422 拒绝；当前用户只从登录令牌中取得。
- 步骤 01 中遍历全部数据表检查用户归属列的自动化测试，会同时覆盖这三张新表。
