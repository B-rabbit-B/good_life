# 步骤 10 附近餐厅推荐：设计

对应步骤文档：docs/10-附近餐厅推荐.md。依赖步骤 04（引擎）与 08（智能体）。

## 已定的选择

1. 高德密钥由服务端统一配置，写在后端本机的 .env 里，不进仓库；Claude 不接触真实密钥。
2. 既做应用接口，也给聊天智能体加一个“附近餐厅推荐”工具。
3. 需求转检索关键词：固定需求词表，先用规则匹配，匹配不上再让对话模型从词表里挑，词表外的词丢弃；最终过滤与排序只由规则决定。
4. 约束过滤用方案 A：餐厅类型表，每类配营养库里的代表菜，由步骤 04 的引擎按用户当天的约束评价代表菜，得出整类结论与“可点、适量、应避开”。

## 模块结构

新增包 app/restaurants：

- amap.py：高德 Web 服务客户端。周边搜索（v5 place/around，类型限定餐饮服务 050000，带 business 字段取评分）、地址解析（v3 geocode/geo，把手动输入的地点解析成坐标与区县）、逆地理（v3 geocode/regeo，仅在保存粗略区域且来源是坐标时调用）。基础地址与超时来自配置。高德的状态码映射为本应用的错误（密钥无效、额度用完、请求太频繁、其他失败）。密钥不出现在日志、错误与响应里。
- coords.py：WGS-84 转 GCJ-02 的本地换算（中国境外的坐标原样返回），不额外调用接口。
- data/restaurant_types.json：约 18 类餐厅。每类有键、中文名、高德类别编码、店名关键词、3 至 5 个营养库食物编号作为代表菜。
- data/needs.json：约 12 个需求词。每个词有同义说法、高德检索关键词（最多 3 个）、偏向的餐厅类型。
- types.py：判断一家店的类型（店名关键词优先，其次具体类别编码，“中餐厅”等笼统编码最后；都对不上为未知类型），以及用引擎评价代表菜得出整类结论。
- needs.py：规则匹配需求词；可选地让对话模型从词表里挑（JSON 写在正文里，词表外的词丢弃，模型失败时退回无需求）。
- ranking.py：过滤与排序。
- service.py：检索推荐的完整流程、设置读写、频率限制。
- models.py、schemas.py、router.py：表、请求响应模型、接口。
- live_check.py：用真实高德密钥跑验证场景的实测脚本。

## 数据

新表 restaurant_settings，每个用户一行：

- user_id（唯一）
- location_consent：not_asked、granted、denied，默认 not_asked
- consent_updated_at（可空）
- area：加密 JSON，可空，内容为区县名称、行政区编码、取整到小数点后两位的中心经纬度（GCJ-02）
- area_saved_at（可空）
- created_at、updated_at

精确坐标、手动输入的地点原文与每次检索的内容都不入库，没有检索历史。迁移 0016_restaurants，表总数变为 28 张。

## 接口

前缀 /api/restaurants，都依赖 require_nutrition_user：

- GET /settings：授权状态、是否应询问定位（仅在 not_asked 时为真）、粗略区域名称与保存时间。
- PUT /settings/consent：设为 granted 或 denied。
- DELETE /settings/area：清除粗略区域，返回 204。
- GET /needs：需求词表（键、中文名、说明），供前端显示可点选的标签。
- POST /search：检索推荐。地点三选一：坐标（经纬度加坐标系 gps 或 gcj02，要求已授权）、手动地点（文字加可选城市）、使用已保存的粗略区域。可选：一句话需求（最长 100 字）、需求词键（最多 3 个）、半径（500 至 5000 米，默认 2000）、是否记住大致区域（默认否）。

检索结果：

- center：中心点名称与来源（gps、place、saved_area）。精确坐标不回传。
- needs：用到的需求词与来源（rules、model、none）。
- restaurants：最多 20 家。每家有高德店铺编号、名称、类型键与名称、距离（米）、评分（高德有提供时）、地址、结论（suitable、caution、unchecked）、导航链接。
- type_advice：本次结果中出现的每个类型的结论、可点、适量、应避开（菜名）与引擎原因。
- avoided_types：被避开的类型、原因（原样来自引擎）与被避开的店名。
- notice：“到店可点与应避开是基于餐厅类别的一般性建议，不代表该店真实菜单，也不保证该店有这些菜。”
- disclaimer：引擎的免责声明。

导航链接用高德官方网页导航地址（终点为店铺坐标与名称，方式默认步行，带来源标识与唤起客户端参数），手机上会唤起高德地图，没有安装则打开网页版。接口清单把它单列为“导航跳转”。

## 规则

类型判断：店名关键词优先，然后是具体的高德类别编码，笼统编码（如中餐厅 050100、餐饮服务 050000）最后，都对不上为未知类型。

整类结论：用 build_context 与 evaluate_food 按用户当天的约束评价每道代表菜，克数取该食物的默认克数。

- 一半以上为不建议：建议避开（not_recommended）。
- 否则有任何一道不建议或需注意：需要注意（caution）。
- 否则：适合（suitable）。
- 适合的代表菜进“可点”，需注意的进“适量”，不建议的进“应避开”；原因去重后原样取自引擎。
- 未知类型的店结论为未核对（unchecked），不给点菜建议，只提示“请到店自行留意”。

需求解析：先规则（同义说法命中）；没有命中且一句话需求不为空、用户分配了对话模型时，请模型从词表里挑最多 3 个；仍没有则不限需求。直接传入的需求词键与规则结果合并去重。

检索：有需求时每个检索关键词发一次周边搜索，最多 3 次；没有需求时按餐饮服务类型发一次。结果按店铺编号去重合并。

排序：

1. 被判为建议避开的店不进推荐列表，只出现在 avoided_types。
2. 先按结论：适合，然后需要注意，然后未核对。
3. 再按是否属于需求偏向的类型。
4. 再按距离由近到远。
5. 最后按评分由高到低。
6. 截取前 20 家。

## 位置与授权

- 坐标检索要求 location_consent 为 granted，否则返回 409，提示改用手动输入地点，不提示去授权。
- 拒绝状态保存在服务端；查看设置时只在 not_asked 下返回“应询问”；智能体工具没有坐标参数，也不会索要授权。只有用户自己改回 granted 才恢复。
- 勾选“记住大致区域”时才保存粗略区域：来源是手动地点时用地址解析得到的区县；来源是坐标时调用一次逆地理取区县。中心坐标取整到两位小数（约 1 公里）。
- 用户可随时清除粗略区域。

## 聊天工具

- SDK 新增只读能力 restaurants_recommend，SDK 版本 1.2，共 34 项能力；MCP 工具变为 28 个。需本人确认的 6 项不变。
- 参数：place（可选）、city（可选）、needs（需求词键，最多 3 个，枚举取自词表）、radius（可选）。没有坐标参数。
- 没有 place 时用已保存的粗略区域；仍没有则返回“需要地点”的错误，智能体据此问用户在哪里。
- 返回给模型：排在前面的 8 家（名称、类型、距离、结论、可点菜名）、已避开的类型名称、固定提示。不把“应避开”的菜名交给模型。
- 只有档案可用且服务端配置了高德密钥时才提供该工具；系统指令增加一句“餐厅推荐只是按类别的一般性建议，不代表真实菜单”。
- 步骤 08 的输出检查不变：回答里出现的菜名（包括店名里带的）照常检查，命中医嘱阻断的会被拦截改写。

## 错误

| 情况 | 状态码 | 错误码 |
|---|---|---|
| 未配置高德密钥 | 503 | restaurant_not_configured |
| 高德额度用完或太频繁 | 503 | restaurant_service_busy |
| 网络错误或高德其他失败 | 502 | restaurant_service_failed |
| 本应用频率限制（每用户每小时 30 次检索） | 429 | restaurant_rate_limited |
| 手动地点找不到 | 422 | restaurant_place_not_found |
| 传坐标但未授权 | 409 | restaurant_location_not_granted |
| 没给任何地点，或选了已保存区域但没有保存 | 422 | restaurant_no_location |

频率限制在进程内计数，单进程部署下有效，文档注明。

## 配置

.env 新增：AMAP_KEY（可空，空则功能关闭）、AMAP_BASE_URL（默认 https://restapi.amap.com，测试与代验时指向本机模拟服务）、AMAP_TIMEOUT_SECONDS（默认 8）。.env.example 只写占位说明。

## 测试与验收

- 自动化测试用 httpx 的模拟传输返回一组固定的店：川菜馆、粥铺、轻食店、火锅店、麻辣烫、面馆、无法判断类别的餐厅，按 7 条验收标准逐条测试。另测坐标换算（已知坐标对）、类型判断、需求解析（含模型挑词与非法词丢弃）、排序、错误映射、密钥不外泄、数据库里没有精确坐标且粗略区域为密文、清除后为空、别的用户 404、路由准入、SDK 与 MCP 清单、智能体工具装配与输出检查。
- 代验：启动真实后端，把 AMAP_BASE_URL 指向本机模拟高德服务，按 7 条标准逐条操作接口并核对数据库。
- 实测脚本 app.restaurants.live_check：读取 .env 里的真实密钥，建临时用户，跑 3 个城市（北京国贸、上海人民广场、成都春熙路）乘 3 种用户（普通、忌辛辣医嘱、减脂），外加一次手动地点与一次 GPS 坐标检索，结果写入 backend/restaurant_live_result.md（不进仓库），全文按密钥脱敏，结束时删除临时用户。由用户运行，结果作为“验证场景记录”。
- 第 1、2 条的真实检索依赖用户运行实测脚本，本步骤预计为有条件通过。
