# 步骤 08 智能体层 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 做出会多轮聊天、会用工具、按个人档案动态装配、会主动开场的智能体；关键动作（医嘱确认与解除）结构上碰不到；回答发出前对照硬约束做输出检查；饮食建议的依据由程序从步骤 04 引擎的依据条目生成；偏好记忆与医嘱严格分开。满足 `docs/08-智能体层.md` 的 9 条验收标准（第 1、2、9 条的真实模型表现由用户运行实测脚本补充）。

**Architecture:** 新增 `app/agent` 包，自写一个结构清晰的小循环（装配 → 调模型 → 执行工具 → 回到模型 → 输出检查 → 附依据与免责 → 保存 → 分段推送）。模型调用走步骤 07 的统一入口（本步骤补上工具结果回传、停止原因、各厂商跨轮状态、Gemini 参数结构清洗、按用途解析一次目标）；工具调用走步骤 06 的 SDK，使用只能在服务端构造的智能体凭证和过滤掉“需本人确认”能力的能力表。风险话题、医嘱线索、输出检查、依据、开场都由规则决定，模型只负责理解与措辞。

**Tech Stack:** Python 3.12、FastAPI（StreamingResponse 输出 text/event-stream）、SQLAlchemy 2、PostgreSQL 16、Alembic、httpx2、pytest。不新增依赖，不用 LangGraph、mem0（用户已确认）。

**Spec:** `docs/08-智能体层.md`。设计已在对话中由用户确认：自写简单循环、自建偏好表、模拟模型自动化测试加用户运行实测脚本。另需满足步骤 06、07 评审带入的要求：智能体不得持有用户登录令牌、碰不到需本人确认的能力（有测试）；统一调用入口补齐工具回传、跨轮状态、停止原因、Gemini 参数结构；每个循环只解析一次用途模型。

## 关键决策

| 决策 | 内容 | 理由 |
|---|---|---|
| 编排 | 自写小循环，节点划分参照 LangGraph 的思路：装配、调模型、执行工具、输出检查、收尾；每轮最多 6 次模型调用 | 用户选定；与步骤 07 自写适配层一致，可控、好测 |
| 流式输出 | 先生成完整回答并通过输出检查，再按段（每段约 20 个字）以 text/event-stream 推送；同时提供非流式的 JSON 模式 | 回答必须先检查再发出，不能把未检查的模型原始输出推给用户 |
| 智能体凭证 | `AgentCredential(user_id)` 只能在服务端代码里构造，不对应任何令牌；能力表为步骤 06 对外暴露的 26 项；审计里凭证类型为 agent、客户端名为 agent | 步骤 06 评审要求：结构上碰不到需本人确认的能力 |
| 工具装配 | 经期工具只在经期模块开放时提供；健身查询类工具（周汇总、趋势、训练列表、今日训练信号）只在用户有训练记录时提供，记录训练始终提供；医嘱、饮食、档案能力与偏好工具始终提供 | 规格：按档案动态装配 |
| 风险话题 | 用户消息命中药物与剂量、孕期异常、严重症状、极端节食、自伤等关键词时，不调用模型，直接用固定安全回复（不给具体指导，引导就医） | 验收第 6 条要求确定性 |
| 输出检查 | 识别回答里出现的营养库食物，逐个用引擎为本人判断；医嘱判为不建议的食物出现在推荐语气里就拦截：让模型重写一次并复查，仍不通过就换成固定的安全回答 | 验收第 2 条 |
| 依据 | 回答里提到的食物，其引擎依据（来源、说明、依据编号）由程序整理成“依据”段附在回答后；模型的原文里不得自称依据 | 验收第 7 条：依据不允许编造 |
| 医嘱线索 | 规则识别“医生说我好了、可以不用忌口、复查正常”等说法，并在系统指令里提示只能提出解除建议；确认与解除工具本就不存在 | 验收第 3 条 |
| 开场 | 规则按优先级挑出今天最该问的一个问题；同一天同一类只问一次；拒绝后当天不再问；可整体关闭；模型只负责措辞，失败时用固定模板 | 验收第 4 条 |
| 偏好记忆 | 自建加密偏好表；智能体通过“记住偏好”工具写入，写入前过滤医嘱、用药、过敏、病情类内容；用户可查看与删除；医嘱永远从医嘱模块读取 | 用户选定；验收第 8 条 |

**Interfaces:**
- Produces（`app.llm.adapters.base`，向后兼容地扩展）：
  - `ChatMessage(role: "system" | "user" | "assistant" | "tool", text: str, images=(), tool_calls: tuple[ToolCall, ...] = (), tool_call_id: str | None = None, tool_name: str | None = None, provider_state: dict | None = None)`；规则：只有 user 可带图片；只有 assistant 可带 tool_calls 与 provider_state；tool 必须带 tool_call_id 与 tool_name，text 为工具结果（JSON 文本）
  - `ToolCall(name, arguments, call_id, provider_state: dict | None = None)`（Gemini 的 thoughtSignature 等放在这里）
  - `ChatResult` 增加 `finish_reason: "stop" | "tool_calls" | "length" | "content_filter" | "other"` 与 `provider_state: dict | None`（例如 DeepSeek 的 reasoning_content）；已有字段不变
  - `FINISH_REASONS` 常量；`sanitize_schema_for_gemini(schema: dict) -> dict`（去掉 Gemini 不认的键：title、additionalProperties、$defs 内联展开、default、examples 等，保留 type、properties、required、items、enum、description、format（只保留 Gemini 支持的 date-time 等）、nullable）
- 各厂商格式：
  - OpenAI 兼容：assistant 带工具调用时为 `{"role": "assistant", "content": 文本或 null, "tool_calls": [{"id", "type": "function", "function": {"name", "arguments": JSON 文本}}]}`；provider_state 含 reasoning_content 时原样回传在该 assistant 消息上；tool 消息为 `{"role": "tool", "tool_call_id", "content"}`；finish_reason 取 `choices[0].finish_reason`（stop、tool_calls、length、content_filter，其余为 other）；结果的 provider_state 取 message.reasoning_content（存在时）
  - Claude：assistant 的 content 为 text 块加 `{"type": "tool_use", "id", "name", "input"}` 块；连续的 tool 消息合并为一条 user 消息，content 为 `[{"type": "tool_result", "tool_use_id", "content"}]`；stop_reason 映射：end_turn、stop_sequence 为 stop，tool_use 为 tool_calls，max_tokens 为 length，refusal 为 content_filter
  - Gemini：assistant 为 role model，parts 为 text 与 `{"functionCall": {"name", "args"}}`（ToolCall.provider_state 里的 thoughtSignature 放回同一个 part）；tool 为 role user、part `{"functionResponse": {"name", "response": {"result": 解析后的 JSON 或原文}}}`；结果里的 functionCall 没有 id 时用 `gemini-call-<序号>` 作为 call_id，thoughtSignature 存进 ToolCall.provider_state；工具声明改用 `parametersJsonSchema`（若不被接受则退回用 `sanitize_schema_for_gemini` 后的 `parameters`，实现时以公开文档为准，测试覆盖所选做法）；finishReason：STOP 为 stop，MAX_TOKENS 为 length，安全类为 content_filter，有 functionCall 时为 tool_calls
- `app.llm.service`：`ResolvedTarget`（frozen：kind、base_url、api_key（repr=False）、model_id、provider_name、model_pk、capabilities）；`resolve_target(user_id, purpose) -> ResolvedTarget`（与现在 complete 内部的读取与检查相同，用自己的短会话）；`complete(user_id, purpose, messages, *, tools=(), max_tokens=1024, factory, target: ResolvedTarget | None = None)`：给了 target 就不再读库，但仍在调用前做能力检查（图片、工具）与地址复查

### Task 6: 对话循环与聊天接口

**Files:**

- Modify: `backend/app/agent/router.py`, `schemas.py`

**Interfaces:**
- Consumes: 任务 1 的 `resolve_target`、`complete(target=...)`、扩展后的 ChatMessage；任务 2 的 `AgentCredential`、`agent_registry`、`tool_name`、`tool_description`、`capability_for_tool`；任务 3 的会话与偏好；任务 4 的 safety、clues、assembly；任务 5 的 guard
- Produces（`app.agent.loop`）：
  - `MAX_MODEL_CALLS = 6`；`TurnResult(message_id, text, evidence, flags: tuple[str, ...], tools_used: tuple[str, ...])`；flags 取值：risk_<类别>、guard_rewritten、guard_fallback、resolution_clue、tool_limit
  - `run_turn(user_id, conversation_id, user_text, *, today, factory) -> TurnResult`，步骤固定：
    1. 保存用户消息；`classify_risk` 命中 → 回复 SAFE_REPLIES[类别]（不调模型、不调工具），flags 记 risk_<类别>，保存并返回
    2. `load_context`、`detect_resolution_clue`、`select_tools`、`build_system_prompt`；`resolve_target(user_id, "chat")` 一次（未配置时 `agent_model_not_configured` 409，提示去设置页选对话模型）
    3. 消息 = 系统指令 + 最近 40 条历史（用户与助手的文本，以及本轮之前保存的工具往返） + 本条用户消息
    4. 循环：`complete(..., target, tools=工具声明)`；有 tool_calls 就逐个执行（`remember_preference` 走偏好表，其余用 `capability_for_tool` 找能力，不存在的工具名返回“没有这个工具”的错误结果；能力用 `GoodLife(registry=agent_registry()).call(AgentCredential(user_id), ..., client_name="agent")`；SdkError 转成结构化错误结果交回模型），把 assistant 消息（含 provider_state）与工具结果追加进消息并保存；直到 finish_reason 不是 tool_calls 或用满 MAX_MODEL_CALLS（用满时用最后一次的文本，flags 记 tool_limit）
    5. 输出检查：`find_foods` → 对每个食物用 `nutrition.evaluate_food`（默认份量）取得引擎判断 → `check_answer`；不通过时追加 REWRITE_INSTRUCTION 让模型重写一次（不带工具）并再查；仍不通过 → SAFE_FALLBACK，flags 记 guard_fallback；重写通过记 guard_rewritten
    6. 最终文本不得包含模型自写的“依据：”段（若有则去掉该段）；附上 `evidence_section`；回答涉及饮食、运动或健康建议（提到食物、调用过饮食、健身或医嘱工具）时附 HEALTH_DISCLAIMER
    7. 保存助手消息（text、evidence、flags）；返回
  - 模型调用失败（AppError 来自 llm）→ 向用户返回可读错误（`agent_model_error`，带原因），用户消息仍保存
- 接口：POST `/api/agent/conversations/{conversation_id}/messages`，请求 `{"text": 1 至 2000 字, "stream": true（默认）}`；`stream` 为真时返回 `text/event-stream`：若干 `event: delta`（`data: {"text": 片段}`），最后 `event: done`（`data: {"message_id", "evidence", "flags", "tools_used"}`）或 `event: error`（`data: {"code", "message"}`）；为假时返回 JSON（字段同 done 加 text）。路由在调用 run_turn 前结束自己的读事务。
- `tests/agent_fake.py`：`ScriptedModel`，基于 MockTransport 的 OpenAI 兼容格式模拟服务（另提供 Claude 格式），按脚本依次返回：文本、工具调用（可指定工具名与参数）、或“回显系统指令中的某段”；记录每次请求的消息、工具声明与模型名；提供 fixture：为测试用户建立服务与对话用途模型，并覆盖 `get_adapter_factory`。
