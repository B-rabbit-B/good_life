# 位置授权与数据处理说明

本文说明附近餐厅推荐如何取得位置、位置会发给谁、保存什么、不保存什么，以及用户如何清除。内容按实际代码写成，对应后端 app/restaurants 目录（设置与检索流程在 service.py，表在 models.py，高德客户端在 amap.py，坐标换算在 coords.py）。

## 1. 三种给出地点的方式

每次检索只能三选一，同时给两种会被请求格式检查拒绝（422，validation_error）；一种都没给时返回 422，错误码 restaurant_no_location，提示输入地名或地标。

| 方式 | 请求里的字段 | 是否需要定位授权 | 检索中心的名称 |
|---|---|---|---|
| 坐标 | location：经度、纬度与坐标系（gps 或 gcj02，默认 gps） | 需要，授权状态必须是 granted | 固定为“你的当前位置” |
| 手动地点 | place：地名或地标，1 至 50 个字；可加 city：城市，1 至 20 个字 | 不需要 | 高德地址解析返回的格式化地址（例如“北京市朝阳区国贸”） |
| 已保存的大致区域 | use_saved_area 设为真 | 不需要 | 保存时的区域名称（区县、城市或省份） |

手动地点是不授权定位时的替代方式，任何授权状态下都可以用。

## 2. 定位授权

授权状态保存在服务端（restaurant_settings 表的 location_consent 列），每个用户一行，取值：

- not_asked：从未询问过，新用户的默认值。
- granted：用户同意使用定位。
- denied：用户拒绝使用定位。

规则：

1. 查看设置（GET /api/restaurants/settings）时，只有在 not_asked 下 should_ask_location 才为真，前端据此决定要不要询问一次。用户第一次查看设置时，服务端会为他建一行 not_asked 的设置。
2. 用户的选择通过 PUT /api/restaurants/settings/consent 提交，只接受 granted 或 denied，同时记下 consent_updated_at。没有办法把状态改回 not_asked，所以拒绝之后 should_ask_location 一直为假，系统不会再次索要。
3. 授权状态不是 granted（包括 not_asked 与 denied）时用坐标检索，返回 409，错误码 restaurant_location_not_granted，说明里只建议改用手动输入地点（地名或地标，可加上城市），不提示去授权，也不会向高德发出任何请求。
4. 只有用户自己再提交一次 granted，坐标检索才恢复。
5. 聊天智能体使用的“附近餐厅”工具没有坐标参数，只能用用户说出的地名或已保存的大致区域；两者都没有时，工具返回 restaurant_no_location，说明里请智能体问用户在哪里、请用户说出地名或地标，不提定位授权。系统指令里也写明“不要向用户索要定位授权，需要地点时请用户说出地名或地标”。

## 3. 坐标的换算

手机定位给出的是 GPS 坐标（WGS-84），高德使用 GCJ-02。坐标系为 gps 时，后端在本机用公开的标准算法换算成 GCJ-02，不调用任何接口；中国境外的坐标原样使用。坐标系为 gcj02 时原样使用。

## 4. 每次检索会发给高德什么

检索由后端发起，用的是服务端配置的高德密钥（AMAP_KEY），用户的设备不直接连高德。发给高德的内容：

- 周边搜索：检索中心的坐标（GCJ-02，保留六位小数）、半径（500 至 5000 米，默认 2000）、餐饮服务类别编码，以及由需求得出的检索关键词（有需求时）。
- 地址解析：手动输入的地点文字与城市（只在用手动地点时调用）。
- 逆地理：检索中心的坐标（只在用坐标检索、并且勾选了“记住大致区域”时调用一次，用来取得区县名称）。

高德是第三方服务，上述内容会按高德自己的规则处理。本应用不把用户编号、用户名或档案内容发给高德。

## 5. 不保存的内容

以下内容只在一次请求期间使用，不写入数据库，也不写入日志与审计：

- 精确坐标（用户提交的与换算后的都不保存）；
- 手动输入的地点文字与城市；
- 一句话需求与需求词；
- 检索结果（店名、地址、距离、结论等）。

没有检索历史。检索结果里也不回传检索中心的精确坐标：中心只有名称与来源（gps、place、saved_area）。每家店带有导航链接，链接里是这家店本身的坐标与店名（店铺的公开位置，不是用户的位置）。

## 6. 只在用户选择时保存的粗略区域

检索请求里的 remember_area（记住大致区域）默认为假。只有设为真时，才在检索成功后保存一个粗略区域：

- 用手动地点检索时：用地址解析结果里的区县、城市、省份与行政区编码，不再调用逆地理。
- 用坐标检索时：调用一次逆地理，取区县、城市、省份与行政区编码。
- 用已保存的区域检索时：不重新保存。

保存的内容是一个加密的 JSON（restaurant_settings 表的 area 列，用步骤 01 的字段加密密钥加密，数据库里是密文），只有四项：

- name：区域名称，依次取区县、城市、省份，都没有时用固定的“大致区域”。从不使用高德的格式化地址（可能细到街道门牌），也不使用用户输入的地点原文。
- adcode：行政区编码。
- lng、lat：检索中心坐标取整到小数点后两位（约 1 公里）。

同时记下保存时间 area_saved_at。再次勾选会覆盖原来的区域。查看设置时只返回区域名称与保存时间，不返回坐标与编码。

## 7. 清除

DELETE /api/restaurants/settings/area 清除粗略区域，area 与 area_saved_at 都改为空，返回 204。清除之后选择“使用已保存的区域”会返回 422，错误码 restaurant_no_location，提示直接输入地点。删除用户账号时，这一行设置随用户一起删除。

## 8. 表结构

restaurant_settings 表（迁移 0016_restaurants），每个用户最多一行（user_id 唯一）：

| 列 | 内容 |
|---|---|
| id | 主键 |
| user_id | 所属用户，删除用户时级联删除 |
| location_consent | not_asked、granted、denied，默认 not_asked |
| consent_updated_at | 最近一次提交授权选择的时间，可空 |
| area | 加密的粗略区域（name、adcode、lng、lat），可空 |
| area_saved_at | 保存粗略区域的时间，可空 |
| created_at | 建立时间 |
| updated_at | 修改时间 |

所有读写都从当前登录用户出发，任何接口都不接受客户端传入用户编号，别的用户的设置不会被读到或改到。

## 9. 日志、错误与密钥

- 高德密钥只来自服务端配置，不出现在日志、错误说明、响应、审计与实测结果里；高德客户端的文字表示也不含密钥。
- 后端的 HTTP 客户端（httpx2）会在 INFO 级别记录请求地址。高德的请求地址的查询串里有密钥、坐标、地点文字与检索关键词，所以这个记录器上加了过滤：整个查询串一律改写成占位符，只保留路径，新增的参数也一并覆盖。
- 高德返回的错误原文不带进本应用的错误说明，错误说明是固定的中文文字。
- 通过 SDK 或 MCP 调用时，审计只记能力名称、结果、错误码、客户端名与耗时，不记参数与结果。

## 10. 智能体会话里的地点

用户在聊天里说出的地点，本来就在用户自己的那条消息里。智能体调用“附近餐厅”工具时，工具参数（用户说的地名与城市）与工具结果里的 center_name（高德的格式化地址）会作为会话的一部分，保存在步骤 08 的智能体会话历史里。这部分内容整体加密保存，随会话一起删除。工具结果交给模型的只有排在前面的至多 8 家（店名、类型、距离、结论、可点的菜名）、已避开的类型名称与固定提示，不含地址、坐标、导航链接、应避开的菜名与原因。应用接口与 SDK 的检索都不保存工具参数与中心名称。这一点列在验收记录的“需要你确认的设计决定”里。

## 11. 频率限制

每个用户每小时最多检索 30 次，按滑动窗口计算；超过时返回 429，错误码 restaurant_rate_limited。计数在检索开始时进行，所以没有成功的检索（例如地点找不到、坐标未授权）也计入。计数只保存在后端进程的内存里，不入库：后端重启后清零，多个进程各自计数，只在单进程部署下有效。
