## 需要你确认的设计决定

下面这些规则是实现时定下的，步骤文档没有写死具体做法。你若不认同任何一项，告诉我改成什么即可。

1. 高德密钥由服务端统一配置在后端本机的配置文件里（AMAP_KEY），用户不需要也不能自己填；没有配置时附近餐厅功能关闭：检索推荐返回 503 restaurant_not_configured，智能体也不提供这个工具。
2. SDK 能力名只能是“模块.动作”，模块只能是已有的五个之一，所以设计里的 restaurants_recommend 实际命名为 nutrition.nearby_restaurants，随饮食模块开放。
3. 需求用固定的 12 个需求词：先规则匹配，规则没有命中时，只有应用接口的检索才请对话模型从词表里挑词，词表以外的词丢弃；SDK、MCP 与智能体的工具只接受词表里的键，由智能体自己挑。检索关键词、过滤与排序全部由规则决定。
4. 约束过滤用餐厅类型表：18 类，每类 3 至 5 道营养库里的代表菜，由步骤 04 的引擎按用户当天的约束逐道评价；不建议的代表菜占一半以上（含一半）才整类避开，否则有不建议或需注意的为需要注意。按引擎现算的结果（只有一条医嘱、没有每日需求时）：忌辛辣避开川菜、湘菜、麻辣烫与串串；忌生冷避开日料；忌油腻避开快餐炸鸡汉堡；忌海鲜避开海鲜、日料、麻辣烫与串串；低盐饮食避开麻辣烫与串串；忌甜食避开甜品饮品；禁酒不避开任何类型。只到需要注意的：忌辛辣时的火锅（只有“火锅”这一道菜不建议，应避开里列出“火锅”与医嘱原因）；痛风忌高嘌呤时的海鲜（只有牡蛎带高嘌呤标签）以及火锅、麻辣烫与串串；低盐饮食在没有每日需求时川菜仍为适合。完整的表见《约束过滤与排序规则说明》第 7 节，由文档检查用引擎重算核对。
5. 为了让忌辛辣能在烧烤里命中、忌生冷能在日料里命中，往步骤 04 的营养库里加了烤羊肉串与生鱼片两道菜；日料的第三道代表菜用原有的凉拌黄瓜代替鸡蛋羹（代表日料店的冷前菜），这样忌生冷时日料 3 道里 2 道不建议、整类避开。烤羊肉串另加了别名“羊肉串”：营养库里原有不带辛辣标签的成分条目“羊肉串（烤）”，加别名之后，回答里说“羊肉串”时智能体的输出检查按带辛辣标签的烤羊肉串判断，忌辛辣的用户会被拦截；检索“羊肉串”排第一的也变为这道菜。
6. 判断不出类型的店不过滤，结论为未核对，不给点菜建议，排在最后。
7. 坐标检索要求授权为 granted；没有授权时返回 409，说明里只建议输入地点，不提示去授权。拒绝状态保存在服务端，没有办法改回“未询问”，所以拒绝之后不会再被询问；只有用户自己提交 granted 才恢复。
8. 粗略区域只在用户勾选“记住大致区域”时保存，内容为区域名称、行政区编码与取整到小数点后两位的坐标，加密存储；名称依次取区县、城市、省份，都没有时用“大致区域”，从不使用街道级的地址。用坐标检索并勾选时，为取区县名称额外调用一次高德逆地理。
9. 频率限制每用户每小时 30 次，在检索开始时计数，失败的检索也计入（地点找不到也会消耗高德额度）；计数在后端进程内，只在单进程部署下有效。
10. 词表以外的需求词键返回单独的错误码 restaurant_unknown_need（422），设计里的错误表没有列这一项。
11. 后端 HTTP 客户端的请求日志把整个查询串换成占位符，而不是只遮住密钥，这样坐标、地点与检索关键词也不进日志，以后新增的参数也一并覆盖；代价是排查问题时日志里看不到请求参数。
12. 智能体使用这个工具时，工具参数（用户说出的地名与城市）与工具结果里的 center_name（高德的格式化地址）会作为会话的一部分保存在智能体会话历史里，整体加密，随会话一起删除。用户自己的那条消息本来就含有同样的地点文字。应用接口与 SDK 的检索都不保存工具参数与中心名称。如果你不希望会话历史里出现格式化地址，可以把 center_name 改成只给区县名称，或者从工具输出里去掉。
13. 交给智能体（以及 MCP 客户端）的只有排在前面的至多 8 家（店名、类型、距离、结论、可点的菜名）、被避开的类型（类型名称与原因来源，例如“医嘱”“当日摄入”，让智能体能说明为什么避开）与固定提示，不给地址、坐标、导航链接、应避开的菜名与原因原文。智能体说出被避开的类型名时，如果类型名里带着被医嘱阻断的食物名（例如“麻辣烫与串串”），步骤 08 的输出检查会要求重写并附上医嘱提醒，这是有意的“宁可多拦”。
14. 导航链接用高德官方网页导航地址，默认步行，手机上唤起高德地图，没有安装则打开网页版。

## 已知问题与后续

- 真实检索未运行：第 1、2 条的真实效果与三个城市的推荐结果都还没有数据，需要你运行实测脚本，并把结果摘抄进《验证场景记录》。步骤 07、08 的真实模型实测与步骤 09 的照片评测也仍待补。
- 类型表里的高德类别编码是凭记忆写的（编写时没能打开官方的编码表），店名关键词优先；请对照实测结果里每家店的原始类别编码核对。
- 低盐医嘱：川菜的代表菜都没有带高钠或腌制标签，档案不完整、无法估算每日需求时，低盐医嘱下川菜仍是“适合”；能估算每日需求时因水煮鱼的钠超过上限而为“需要注意”。按已知局限记录。
- 频率限制只在单进程内有效，后端重启后清零；每次检查会顺带清理所有用户的过期记录，用户很多时开销随之增长，单进程演示规模下没有问题。
- 通过 SDK 或智能体调用时，高德额度用完、太频繁或高德出错（429、502、503）归为服务内部错误，智能体看到的提示是通用的稍后再试，可能会立即重试并多消耗一次额度。
- 智能体在没有地点时检查已保存的区域，这一步会为从未打开过附近餐厅设置的用户建一行空的设置（未询问、没有区域），不含任何位置数据。
- 高德返回的店名原样交给模型（作为 JSON 字符串），没有截断；店名里有特别长或奇怪的文字时会进入模型的输入。
- 对忌辛辣的用户，智能体的回答点名火锅店，或者说出已经避开了“麻辣烫与串串”时，店名与类型名里的“火锅”“麻辣烫”会被步骤 08 的输出检查当作被阻断的食物，回答会被要求重写并附上医嘱提醒；这是输出检查按菜名一律检查、宁可多拦的结果。
- 痛风（忌高嘌呤）：营养库里海鲜一类只有牡蛎带高嘌呤标签，所以海鲜店只到“需要注意”，不会整类避开，与忌辛辣时的火锅同理。
- 需求的规则匹配只认词表里写明的说法，例如“少辣一点”不会命中不辣；“要不喝粥吧”里的“不”会被当作否定。
- 高德请求的超时是连接、读取等每个阶段各 8 秒，不是整个请求的总时长；有需求时一次检索最多发 3 次周边搜索。
- 推荐只基于餐厅类别的代表菜，没有经过营养或医学专业人员审核，只是作品集演示，仅供参考。
