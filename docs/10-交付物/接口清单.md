# 接口清单

步骤 10 新增 5 个接口，路径都以 /api/restaurants 开头，在接口文档页面（服务启动后打开 8000 端口下的 docs 页面）的 restaurants 分组里可以直接试用。另外新增一项只读的 SDK 能力，同时作为 MCP 工具与聊天智能体的工具（第 7 节）。导航跳转不是单独的接口，而是检索结果里每家店自带的链接（第 6 节）。

按步骤文档的说法对应关系：

- 按位置检索：第 5 节的检索推荐接口，地点用坐标、手动地点或已保存的大致区域。
- 按需求筛选：同一个检索推荐接口的一句话需求与需求词键；需求词表由第 4 节的接口提供。
- 导航跳转：第 6 节。
- 位置授权与粗略区域：第 1 至 3 节。

通用约定：

- 所有接口都要求已登录、已确认免责声明，并且饮食模块对这个用户开放（与步骤 04 的饮食接口相同）。没有登录返回 401（not_authenticated，令牌失效时为 invalid_token），没有确认免责声明返回 403（disclaimer_not_accepted），饮食模块不可用返回 403（nutrition_not_available）。
- 只能读写自己的设置，任何接口都不接受客户端传入用户编号。
- 请求正文里出现没有声明的字段，或字段格式不对，返回 422，错误码 validation_error，并带每个字段的明细。
- 错误格式统一为一个 error 对象，含 code 与 message；message 是中文说明，并给出下一步建议。本模块的错误码都以 restaurant_ 开头。
- 设置、需求词表这几个接口不依赖高德密钥；只有检索推荐需要服务端配置了高德密钥。
- 位置与数据的处理见《位置授权与数据处理说明》，需求的处理见《需求到检索关键词的映射说明》，结论与排序见《约束过滤与排序规则说明》。

## 1. 查看设置：GET /api/restaurants/settings

返回：

- location_consent：定位授权状态，not_asked、granted、denied 之一。
- should_ask_location：是否应询问定位，只有 not_asked 时为真。
- area：已保存的粗略区域，没有时为空；有时只含 name（区域名称）与 saved_at（保存时间），不含坐标。

用户第一次查看时，服务端为他建一行未询问的设置。

## 2. 提交授权选择：PUT /api/restaurants/settings/consent

请求：consent，只能是 granted 或 denied；填 not_asked 或其他值返回 422（validation_error）。响应与查看设置相同。

## 3. 清除粗略区域：DELETE /api/restaurants/settings/area

清除已保存的粗略区域，返回 204，没有响应正文。没有保存过也返回 204。

## 4. 需求词表：GET /api/restaurants/needs

返回全部 12 个需求词，每个有 key（键）、name（名称）、description（说明），供前端显示可点选的标签。完整的词表见《需求到检索关键词的映射说明》。

## 5. 检索推荐：POST /api/restaurants/search

请求（地点三选一）：

- location：坐标，含 lng（经度，-180 至 180）、lat（纬度，-90 至 90）与 coord_type（gps 或 gcj02，默认 gps）。要求定位授权为 granted。
- place：手动地点，地名或地标，去掉两端空白后 1 至 50 个字。可以再加 city：城市，1 至 20 个字，只能和 place 一起填。
- use_saved_area：设为真表示使用已保存的大致区域。
- need：一句话需求，最长 100 字，可不填。
- needs：需求词键，最多 3 个，可不填。
- radius：检索半径，500 至 5000 米，默认 2000。
- remember_area：是否记住大致区域，默认否。

同时给出两种地点、单独给 city、半径超出范围、坐标超出范围、坐标系不是 gps 或 gcj02，都返回 422（validation_error），不发出任何网络请求。

处理过程：频率限制 → 校验需求词键并按规则匹配一句话需求 → 读设置并结束读事务 → 确定检索中心（坐标换算或地址解析） → 规则没有命中时请对话模型挑词（可选） → 周边检索（每个关键词一次，最多 3 次） → 记住大致区域（可选） → 引擎评价每类代表菜 → 过滤与排序。调用高德与模型期间不占用数据库事务。

响应 200：

- center：检索中心，含 name（名称）与 source（gps、place、saved_area 之一）。不含精确坐标。
- needs：用到的需求词，含 keys、names 与 source（rules、model、none 之一）。
- restaurants：推荐列表，最多 20 家。每家有 id（高德店铺编号）、name（店名）、type_key 与 type_name（类型，未知类型时为空）、distance_m（距离，米，高德没给时为空）、rating（评分，高德没给时为空）、address（地址）、conclusion（suitable、caution、unchecked 之一）、nav_url（导航链接，见第 6 节）、tip（未知类型时为“无法判断这家店的类别，请到店自行留意。”，其他为空）。
- type_advice：本次结果里出现的每个类型（包括被避开的类型）的到店建议，含 type_key、type_name、conclusion（suitable、caution、not_recommended 之一）、order（可点）、moderate（适量）、avoid（应避开）与 reasons。reasons 每条含 food_name（给出这条原因的代表菜）以及引擎原因的 source、effect、code、message、ref。
- avoided_types：被避开的类型，含 type_key、type_name、reasons（同上）与 restaurants（被避开的店名）。
- notice：固定提示“到店可点与应避开是基于餐厅类别的一般性建议，不代表该店真实菜单，也不保证该店有这些菜。”
- disclaimer：引擎的免责声明。

错误：

| 状态码 | 错误码 | 何时出现 |
|---|---|---|
| 503 | restaurant_not_configured | 服务端没有配置高德密钥，附近餐厅功能关闭 |
| 429 | restaurant_rate_limited | 同一用户一小时内检索超过 30 次 |
| 422 | restaurant_unknown_need | needs 里有词表以外的键；不发出网络请求 |
| 409 | restaurant_location_not_granted | 用坐标检索，但定位授权不是 granted；说明里建议改用手动地点，不提示去授权，不发出网络请求 |
| 422 | restaurant_place_not_found | 高德找不到手动输入的地点；建议换个说法或加上城市 |
| 422 | restaurant_no_location | 一种地点都没给，或选了使用已保存的区域但没有保存（或已清除） |
| 503 | restaurant_service_busy | 高德返回额度用完或请求太频繁 |
| 502 | restaurant_service_failed | 连不上高德、超时、高德返回其他错误或无法识别的内容；密钥无效或类型不对时说明里请管理员检查密钥 |
| 422 | validation_error | 请求格式不对，见上 |

频率限制：每个用户每小时最多 30 次，按滑动窗口计算。计数在检索开始时进行，所以通过请求格式检查与密钥检查之后的失败的检索也计入（例如需求词未知、坐标未授权、没给地点、地点找不到、高德出错）；请求格式不对（validation_error）与没有配置密钥（restaurant_not_configured）在计数之前就被拒绝，不计入。计数保存在后端进程的内存里，后端重启后清零；多个进程各自计数，只在单进程部署下有效。

## 6. 导航跳转

导航跳转不需要单独调用接口：检索结果里每家店的 nav_url 就是高德官方的网页导航地址，前端做成一个按钮，点一下即可跳转（一键跳转）。

地址的组成：uri.amap.com 下的 navigation 页面，参数为 to（终点：这家店的经度、纬度与店名，店名按网址规则编码）、mode=walk（默认步行）、src=good-life（来源标识）、coordinate=gaode（坐标是高德坐标）、callnative=1（手机上装了高德地图时唤起客户端，没有安装则打开网页版）。

导航只用这家店本身的坐标与店名，不带用户的位置；用户到了高德里再自行决定怎么去，或另行点外卖。本应用不对接外卖平台，也不代下单。

## 7. SDK 能力、MCP 工具与智能体工具

- SDK 能力：nutrition.nearby_restaurants，只读，随饮食模块开放。SDK 版本升到 1.2，共 34 项能力；其中需本人确认的 6 项不变。
- MCP 工具：nutrition_nearby_restaurants，MCP 工具变为 28 个。
- 聊天智能体：只有服务端配置了高德密钥时才提供这个工具，系统指令随之多一句“附近餐厅推荐只是按餐厅类别给出的一般性建议，不代表该店真实菜单；不要向用户索要定位授权，需要地点时请用户说出地名或地标。”

参数（多余字段一律拒绝，没有坐标参数）：

- place：用户说出的地名或地标，1 至 50 个字；不填表示使用用户在应用里保存的大致区域。
- city：城市，1 至 20 个字，只能和 place 一起填。
- needs：需求词键，最多 3 个，只能从词表的 12 个键里选。
- radius：500 至 5000 米，默认 2000。

输出（应用接口检索结果的精简版）：

- center_name：检索中心的名称。
- restaurants：排在前面的至多 8 家，每家只有 name、type_name、distance_m、conclusion 与 order（这一类可点的菜名）。
- avoided_types：被避开的类型，每个只有 type_name（类型名称）与 reason_sources（这一类原因的来源名称，按引擎的来源顺序去重，例如“医嘱”，或“医嘱”与“当日摄入”），让智能体能说明为什么避开。
- notice：固定提示。

不给地址、坐标、导航链接、店铺编号、应避开的菜名与原因原文。

注意：被避开的类型名称里常带着营养库的食物名（例如“麻辣烫与串串”里的麻辣烫）。智能体在回答里说出这样的类型名时，如果其中的食物被用户的医嘱阻断，步骤 08 的输出检查会照样要求重写，并在回答后附上医嘱提醒。这是有意的“宁可多拦”，不是误报。

错误：没有 place 也没有保存的区域时返回 restaurant_no_location，说明里请智能体问用户在哪里、请用户说出地名或地标，不提定位授权；没有配置高德密钥时返回 restaurant_not_configured；其余错误码与第 5 节相同。通过 SDK 调用时，状态码 422 的错误归为参数有误，429、502、503 的错误归为服务内部错误，错误码原样保留。每次调用都写一条审计，审计不记参数与结果。
