# 验证场景记录

步骤文档要求的交付物之一：一组验证场景，记录不同城市、不同约束下的推荐结果。真实的检索结果必须用真实的高德密钥才能得到，而自动化测试一律用模拟高德、绝不访问真实网络，所以这些场景由附近餐厅实测脚本来跑，由你本人在本机运行。下表的“结果”一栏在你运行实测脚本之后填写。

## 1. 怎样运行

1. 在高德开放平台申请一个“Web 服务”类型的密钥，填到后端本机配置文件 backend/.env 的 AMAP_KEY（这个文件不提交，密钥也不要发给任何人）。
2. 确认数据库在运行、开发库已建到最新版本。
3. 按仓库根目录 README 的“附近餐厅推荐”一节运行附近餐厅实测脚本。脚本读取的高德配置与正式服务完全相同；没有配置密钥时，它会说明怎么配置然后退出。

脚本在开发库里建立 3 个临时用户：

- 普通用户：没有医嘱，目标为维持体重，档案完整（能估算每日需求）。
- 忌辛辣医嘱用户：一条“一周内忌食辛辣”的医嘱，条目已确认；已授权定位，用于 GPS 坐标检索。
- 减脂目标用户：没有医嘱，目标为减脂。

用户名形如 live_ 加 8 位十六进制随机编号再加下划线，后面是用户类别。所有检索都走正式的检索流程（与检索推荐接口相同的服务、真实的高德客户端），只是不请模型挑词。不论正常结束、出错还是中途按 Ctrl+C，脚本最后都会删除这 3 个临时用户；如果进程被强行结束，请手动删除用户名符合这个形式的用户。

## 3. 结果文件里有什么

结果写在 backend/restaurant_live_result.md（已在 backend 的忽略列表里，不提交）。全文按密钥脱敏，不含高德密钥；店名、地址与类别是高德的真实数据，用户只有脚本建立的临时用户。每个场景记录：

- 检索方式、检索中心的名称与来源、用到的需求词与来源、保存的大致区域（只有第 10 行）、推荐列表的总数与耗时；
- 前 10 家：名称、类型、距离、结论、评分，以及高德原始的类别编码与类别名称；
- 被避开的类型、被避开的店名与原因（原因原样来自引擎，带出给出原因的代表菜与依据来源）；
- 各类型的到店建议：结论、可点、适量、应避开。

某个场景出错（例如密钥无效、额度用完、网络不通）时，那一行记下错误码与说明，其余场景照常运行。中途中断时，已完成的场景也会写进去，并注明需要重新完整运行。

## 4. 要特别核对的两件事

1. 高德类别编码：类型表里的编码是凭记忆写的，没有对照官方编码表。请对照结果文件里每家店的高德类别编码与类别名称，看类型表里的编码是否对得上（例如火锅店、川菜馆、粤菜馆、西餐厅、日料店、快餐店、咖啡厅的编码），对不上的告诉我改。
2. 类型判断：看“类型”一栏是否合理，尤其是判断成“未知类型”的店多不多；需要补的店名关键词告诉我加。
