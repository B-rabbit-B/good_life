# 步骤 03 接口清单

本文列出步骤 03 提供的全部医嘱接口，共 18 个。所有接口路径都以 /api/medical 开头（其中有几条路径同时支持两种请求方法，例如查询和修改同一个条目，所以路径条数少于接口条数）。请求与响应的正文都是 JSON 格式，只有上传证据文件用表单上传，下载证据文件返回文件本身。日期一律写成“年-月-日”的格式，例如 2026-09-30。

在线的交互式接口文档由服务自动生成，服务启动后在浏览器打开 8000 端口下的 docs 页面即可查看并直接试用，操作顺序见仓库根目录 README 的“医嘱模块演示”一节。

## 一、访问条件

所有医嘱接口都要同时满足下面的条件，由统一的入口检查，缺一不可：

1. 已登录：请求头带有效的访问令牌，否则返回 401（未登录 not_authenticated，或令牌失效 invalid_token）。
2. 已确认当前版本的免责声明：否则返回 403，错误码 disclaimer_not_accepted。
3. 医嘱模块对该用户开放：判断规则只有一处（步骤 01 的能力清单），本模块不重复实现。目前医嘱模块对所有用户开放，与性别无关，男性、女性、其他性别或未填性别的用户都可以使用，所以错误码 medical_not_available（403，医嘱功能当前不可用）现在实际不会出现，它是为将来能力清单关闭该模块预留的。

通过检查后，入口还会在处理请求前先按“今天”刷新当前用户的条目状态（到期转待复核、过期的待确认转已作废），因此任何接口看到的状态都与今天一致。

有一项自动化检查负责把关：它会逐个检查所有 /api/medical 开头的接口，只要有一个没有挂上上述统一入口，测试就会失败。

其他约定：

- 任何接口都不接受客户端传入用户编号，请求里带了多余字段会被 422 拒绝（错误码 validation_error）。
- 别人的记录与不存在的记录一样返回 404，错误码 not_found，不暴露记录是否存在。
- “今天”由服务统一提供，服务层不自行取系统日期，因此测试中可以固定为某一天。
- 条目和当前约束的返回内容不包含药物剂量或相互作用判断；涉及用药的内容一律提示遵医嘱或咨询医生、药师。

## 二、接口一览

所有接口都需登录、需已确认免责声明、需医嘱模块开放，下表不再重复；这三项对应的错误码（not_authenticated、invalid_token、disclaimer_not_accepted、medical_not_available）以及请求格式不合法时的 validation_error，在“主要错误码”列中不再逐个列出（除非该接口有特别的校验）。

| GET | /api/medical/items/{编号} | 无 | 读取一条条目的详情 | not_found |

### 约束与待复核

| 方法 | 路径 | 请求字段或查询参数 | 用途 | 主要错误码 |
|---|---|---|---|---|
| GET | /api/medical/constraints | 查询参数 category（类别，可不填） | 查询今天的全部医嘱硬约束：生效中和待复核，且生效日期不晚于今天。已解除、已作废、待确认的都不在其中。每条带“是否待复核”和“是否有待处理的解除建议”标记，末尾带一句提醒：以上是你确认过的医嘱约束，请遵医嘱；待复核的条目在你确认解除之前仍按原要求执行，如有疑问请咨询医生。步骤 04 的约束引擎从这里读取 | validation_error（类别取值不合法） |
| GET | /api/medical/reviews | 无 | 查询需要用户处理的条目：待复核的，以及带有待处理解除建议的。步骤 08 的智能体在用户打开应用时读取 | 无 |

## 三、上传证据文件的限制

- 允许的类型只有四种：JPG、PNG、WEBP 图片和 PDF 文件。系统按文件开头的字节判断真实类型，客户端声称的类型不作数；把文本文件改名成图片、类型对不上都会被拒绝。
- 单个文件不能超过 10 MB，也不能是空文件。
- 除了检查文件大小，服务在最外层还对整个上传请求设了大小上限：10 MB 再加 64 KB 的表单余量。超过上限的请求在鉴权之前就被拒绝，返回 413，错误码 evidence_too_large。这样即使是未登录的请求，也不能靠超大请求体占用服务的内存和磁盘。分块传输的超大请求同样会被拒绝。这个上限只针对上传证据的接口，其他接口不受影响。
- 文件内容和文件名加密后存储，只对本人可见。别人访问返回 404，与文件不存在时完全一样。
- 下载时系统按检测到的类型返回，并带有禁止缓存、禁止浏览器猜测类型的头，下载文件名由系统生成。

## 四、条目的返回内容

条目在所有接口里的返回内容一致，包含：

| 字段 | 含义 |
|---|---|
| id、order_id | 条目编号、所属医嘱编号 |
| category | 类别：diet_avoid（饮食禁忌）、diet_require（饮食要求）、medication_diet（用药相关饮食注意）、exercise_limit（运动限制）、other（其他） |
| status | 状态：pending_confirmation（待确认）、active（生效中）、pending_review（待复核）、resolved（已解除）、voided（已作废） |
| origin | 来源：extracted（提取）或 manual（手动补充） |
| confidence、low_confidence | 把握程度（high、medium、low，手动补充的为空）；以及“把握低”标记，把握程度为 low 时为真，界面应突出提示用户核对 |
| content、subjects、source_excerpt | 内容、涉及对象、原文片段 |
| start_date、end_date、review_date | 生效日期、预计结束日期、复查日期 |
| missing_fields、notes | 提取时没能识别的字段、系统给出的提示语 |
| resolution_proposed_at、resolution_reason | 解除建议的时间（为空表示没有待处理的建议）、理由 |
| confirmed_at、closed_at、created_at、updated_at | 确认、结束、创建、最近修改的时间 |

## 五、本步骤新增的错误码

统一的错误格式是：一个 error 对象，包含机器可读的错误码 code 和中文提示 message。步骤 01 已有的通用错误码不再重复，下表只列本步骤新增或本步骤会用到的业务错误码。

| 错误码 | HTTP 状态 | 含义 |
|---|---|---|
| order_in_future | 422 | 医嘱日期不能晚于今天 |
| invalid_item_dates | 422 | 预计结束日期或复查日期早于生效日期；或者修改生效中、待复核的条目时，把生效日期改到了今天之后（提示：生效中的条目不能把生效日期改到今天之后） |
| subjects_required | 422 | 确认或修改生效中、待复核的条目时，饮食禁忌、饮食要求、用药相关饮食注意、运动限制四类条目至少要填一个涉及对象 |
| still_due | 422 | 继续执行时新设置的预计结束日期或复查日期按今天算仍然到期，请设置更晚的日期，或者确认解除 |
| evidence_empty | 422 | 上传的文件是空的 |
| evidence_too_large | 413 | 文件不能超过 10 MB（包括整个上传请求超过上限的情形） |
| evidence_type_not_allowed | 415 | 只支持 JPG、PNG、WEBP 图片或 PDF 文件 |
| item_closed | 409 | 已解除或已作废的条目不能再修改或作废 |
| invalid_transition | 409 | 条目当前的状态不允许这个动作，例如只有待确认的可以确认、只有待复核的可以继续执行、只有生效中或待复核的可以提出解除建议或解除 |
| no_proposal | 409 | 这个条目没有待处理的解除建议，无法撤回 |
| medical_not_available | 403 | 医嘱功能当前不可用。目前医嘱模块对所有用户开放，此错误码暂时不会出现 |
| not_found | 404 | 记录不存在，或者属于别的用户（两者对外表现相同） |

步骤 01 已有、本步骤同样会用到的错误码：not_authenticated（未登录）、invalid_token（令牌失效）、disclaimer_not_accepted（未确认当前版本的免责声明）、validation_error（请求格式或取值不合法）。

## 六、交给步骤 06 的说明：只能由用户调用的操作

条目服务里有六个操作只能由用户本人通过上面的接口触发：确认条目、确认解除、作废、继续执行、修改条目、撤回解除建议。它们会确认、移除、放宽或改写医嘱约束，并且在审计记录里把发起方记为用户。代码里把这六个操作的名称列成了一个固定的清单，并有自动化测试检查清单里的每一项都确实存在。

步骤 06 把服务能力做成大模型可以调用的工具时，这个清单里的操作一个都不能开放给大模型或智能体，否则智能体就能以用户的名义确认或解除约束。智能体唯一可以调用的条目操作是“提出解除建议”：它只记录建议，不改变状态和当前约束，来源记为智能体，最终仍要用户确认解除。
