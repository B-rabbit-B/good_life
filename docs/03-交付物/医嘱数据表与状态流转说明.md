# 步骤 03 医嘱数据表与状态流转说明

本文说明步骤 03 新增的四张数据表，以及医嘱条目的五种状态和状态流转规则。表结构由数据库迁移脚本统一管理：迁移编号 0007 接在步骤 02 的最后一个迁移（0006）之后，一次建出四张表。按顺序执行全部迁移即可在空库中建出全部十一张表。

阅读约定与步骤 01《数据表说明》一致：

- “是否必填”指数据库层面该列能否为空。
- “是否加密”指该列存入数据库时是否已被加密，加密后在数据库里只能看到密文，需要持有加密密钥才能还原。
- 所有时间列都带时区；日期列只有年月日，没有时区。
- 四张表都带 user_id 列，指向 users 的 id，并建有索引；用户被删除时，其医嘱数据一并删除。所有查询都从“只查当前用户的数据”开始，别人的记录与不存在的记录一样返回 404。

## 一、四张表的关系

- 一份医嘱（medical_orders）是用户录入的一段原文，提取之后产生零到多个条目（medical_items）。
- 一份医嘱可以附带零到多个证据文件（medical_evidence），例如医嘱照片或 PDF。
- 每个条目的每次创建、修改和状态变化各写一条审计记录（medical_item_events）。
- 医嘱被删除时，它的条目和证据文件一并删除；条目被删除时，它的审计记录一并删除（数据库外键设置了级联删除）。步骤 03 本身不提供删除医嘱的接口，账号注销时的数据删除放在步骤 12。

## 二、medical_orders（医嘱原文）

每一行是用户录入的一份医嘱，同时保存提取时被忽略的句子和说明，方便用户对照原文核对。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 医嘱唯一标识 | 是（主键） | 否 | 随机生成的唯一编号（UUID） |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| order_date | 医嘱开具日期 | 是 | 否 | 日期；不填时取“今天”，不能晚于“今天”。条目的默认生效日期和相对时间（如“三天”“一个月内”）都以它为起点 |
| source_text | 医嘱原文 | 是 | 是 | 用户录入的全文，1 到 5000 个字符（首尾空白会被去掉）。原文长期保留，方便用户与医生核对 |
| extractor | 提取器名称 | 是 | 否 | 记录是哪个提取器处理的，目前是 rule-based-v1（规则提取器）；步骤 07 换成大模型提取器后会写入新的名称，最长 32 个字符 |
| extraction_notes | 提取时的说明 | 是 | 是 | 解密后包含两项：被忽略的句子（每条含句子原文和被忽略的原因）；整份医嘱层面的提示（例如识别到多个复查时间，或者识别到复查时间却没有提取出任何条目）。没有时两项都是空列表 |
| created_at | 录入时间 | 是 | 否 | 创建时由数据库自动填写 |

## 三、medical_evidence（证据文件）

每一行是挂在某份医嘱下的一个文件，只允许图片和 PDF，文件内容整体加密后存入数据库，只对本人可见。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 文件唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| order_id | 所属医嘱 | 是 | 否 | 指向 medical_orders 的 id，并建有索引；医嘱被删除时一并删除 |
| filename | 用户上传时的文件名 | 是 | 是 | 最长保留 200 个字符；上传时没有文件名则记为“未命名文件”。下载时不使用它，下载文件名由系统生成 |
| content_type | 文件类型 | 是 | 否 | 由系统按文件开头的字节判断，不采信客户端声称的类型。只有四种：image/jpeg、image/png、image/webp、application/pdf |
| size_bytes | 文件大小（字节） | 是 | 否 | 整数；大于 0，不超过 10 MB（10485760 字节） |
| content | 文件内容 | 是 | 是 | 二进制内容加密后存储。读取医嘱列表时不会加载它，只有下载时才读取 |
| created_at | 上传时间 | 是 | 否 | 创建时由数据库自动填写 |

## 四、medical_items（医嘱条目）

每一行是一条结构化的医嘱约束。类别、状态、把握程度、来源、各类日期明文存储，因为需要按它们查询和判断到期；条目的内容、涉及对象、原文片段、解除理由加密存储。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 条目唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| order_id | 所属医嘱 | 是 | 否 | 指向 medical_orders 的 id，并建有索引；医嘱被删除时一并删除 |
| position | 在医嘱中的序号 | 是 | 否 | 从 1 开始，按提取顺序排列；手动补充的条目排在最后 |
| category | 类别 | 是 | 否 | diet_avoid（饮食禁忌）、diet_require（饮食要求）、medication_diet（用药相关饮食注意）、exercise_limit（运动限制）、other（其他）五选一。规则提取器不会产出“其他”，它只用于用户手动补充 |
| status | 状态 | 是 | 否 | pending_confirmation（待确认）、active（生效中）、pending_review（待复核）、resolved（已解除）、voided（已作废）五选一，含义见第七节 |
| origin | 条目来源 | 是 | 否 | extracted（提取器提取）或 manual（用户手动补充） |
| confidence | 提取的把握程度 | 否 | 否 | high（高）、medium（中）、low（低）；手动补充的条目为空。low 的条目在接口返回里带有“把握低”标记，需要用户重点核对 |
| content | 条目的具体内容 | 是 | 是 | 1 到 500 个字符。提取的条目取自原文相应的句子或分句 |
| subjects | 涉及的食物或行为 | 是 | 是 | 字符串列表，最多 30 个，每个 1 到 64 个字符；可以为空列表。饮食禁忌、饮食要求、用药相关饮食注意、运动限制这四类在确认时至少要有一个，“其他”类可以为空 |
| source_excerpt | 来源原文片段 | 否 | 是 | 提取的条目保存提取所依据的原文；手动补充的条目为空 |
| start_date | 生效日期 | 是 | 否 | 提取的条目默认等于医嘱开具日期；手动补充时不填则同样取医嘱开具日期。可以晚于今天，此时条目在生效日期到来之前不算当前约束；但生效中和待复核的条目修改时不能把它改到今天之后 |
| end_date | 预计结束日期 | 否 | 否 | 为空表示长期或暂未确定；填写时不能早于生效日期 |
| review_date | 复查日期 | 否 | 否 | 为空表示没有安排；填写时不能早于生效日期 |
| missing_fields | 提取时没能识别的字段 | 是 | 否 | 字段名列表，目前可能出现 end_date 和 subjects；默认空列表。用户填上对应字段后，该字段自动从列表中去掉；用户确认条目时整个列表清空。内容只有字段名，不含用户原文，所以不加密 |
| notes | 提示文字 | 是 | 否 | 系统写入的固定提示语列表（例如“没有识别到持续时间，请补充预计结束日期，或确认这是长期要求”）。全部是系统固定文案，不含用户原文，所以不加密；默认空列表 |
| resolution_proposed_at | 提出解除建议的时间 | 否 | 否 | 为空表示当前没有待处理的解除建议 |
| resolution_reason | 解除理由 | 否 | 是 | 解除建议的理由，或用户确认解除时填写的理由，最长 500 个字符 |
| confirmed_at | 用户确认生效的时间 | 否 | 否 | 用户确认时写入 |
| closed_at | 结束时间 | 否 | 否 | 条目变为已解除或已作废时写入 |
| created_at | 创建时间 | 是 | 否 | 创建时由数据库自动填写 |
| updated_at | 最近修改时间 | 是 | 否 | 创建时取数据库当前时间，每次修改由数据库一并更新 |

补充说明：

- 条目的日期关系在写入前由服务检查：预计结束日期和复查日期都不能早于生效日期，否则返回 422，错误码 invalid_item_dates。
- 修改生效中或待复核的条目时，生效日期不能改到今天之后（改到今天或更早可以，原样提交也可以），否则返回 422，错误码 invalid_item_dates，提示生效中的条目不能把生效日期改到今天之后，条目保持不变。因为把生效日期往后挪，等于让一条已确认的约束暂时失效。待确认的条目不受这个限制。
- 用户能修改的字段只有六个：类别、内容、涉及对象、生效日期、预计结束日期、复查日期。状态、来源、把握程度等字段不能通过修改接口更改，请求里带了多余字段会被拒绝。
- 已解除和已作废的条目是历史记录，不能再修改，也不再参与任何约束查询，但仍可以按状态查询到。

## 五、medical_item_events（审计记录）

每次创建、修改和状态变化各写一条，只增不改，用来回答“什么时候、因为什么、由谁改变了这条医嘱”。

| 字段 | 含义 | 是否必填 | 是否加密 | 取值说明 |
|---|---|---|---|---|
| id | 记录唯一标识 | 是（主键） | 否 | 随机生成的唯一编号 |
| user_id | 归属用户 | 是 | 否 | 指向 users 的 id，并建有索引 |
| item_id | 所属条目 | 是 | 否 | 指向 medical_items 的 id，并建有索引；条目被删除时一并删除 |
| seq | 严格递增的序号 | 是 | 否 | 由数据库自动生成的递增整数（生成方式为始终由数据库生成，不能手工指定）。同一条目的审计记录按它排序，避免同一时刻的记录顺序错乱 |
| occurred_at | 发生时间 | 是 | 否 | 由服务在写入时取当前时间（协调世界时） |
| action | 动作 | 是 | 否 | 见下表，共十种 |
| from_status | 动作前的状态 | 否 | 否 | 创建时为空；提出解除建议、撤回建议、修改这类不改变状态的动作，它与动作后的状态相同 |
| to_status | 动作后的状态 | 是 | 否 | 五种状态之一 |
| source | 发起方 | 是 | 否 | user（用户本人）、system（系统按规则自动执行）、extractor（提取器）、agent（步骤 08 的智能体）四种 |
| detail | 详情 | 否 | 是 | 记录原因、修改了哪些字段等，见下表；没有详情时为空 |

动作与详情：

| 动作 | 中文含义 | 发起方 | 详情内容 |
|---|---|---|---|
| created | 创建条目 | 提取器（提取的条目）或用户（手动补充的条目） | 无 |
| edited | 修改条目 | 用户 | 被修改的字段名列表 |
| confirmed | 确认生效 | 用户 | 确认时一并修改的字段名列表；确认时没有修改则无详情 |
| review_due | 到期转入待复核 | 系统 | 到期原因（文字，见第八节） |
| expired | 过期自动作废 | 系统 | 原因文字：未确认的条目已过预计结束日期，自动作废 |
| voided | 用户作废 | 用户 | 用户填写的理由（可空）；如果作废时清除了一条未处理的解除建议，另有一项标记“建议已清除” |
| continued | 继续执行 | 用户 | 新的预计结束日期和复查日期（可为空）；如果同时清除了未处理的解除建议，另有一项标记“建议已清除” |
| resolution_proposed | 提出解除建议 | 用户或智能体 | 建议理由 |
| resolution_proposal_cancelled | 撤回解除建议 | 用户 | 无 |
| resolved | 确认解除 | 用户 | 解除理由（可空） |

## 六、哪些明文、哪些加密，为什么

- 明文存储：类别、状态、把握程度、来源、各类日期、序号、发起方、动作名、文件类型和大小、各种时间戳。原因是系统要按它们筛选、排序和判断到期（例如“今天有哪些条目到了复查日”），加密后无法在数据库里直接查询。这些字段不含用户写下的原文。
- 提示语列表和缺失字段列表也是明文：它们只由系统固定文案和字段名组成，不含用户原文。
- 加密存储：医嘱原文、提取时被忽略的句子和说明、条目的内容、涉及对象、原文片段、解除理由、审计详情、证据文件名和证据文件内容。原因是这些是用户的病情、用药和饮食信息，属于高度敏感数据；加密后即使数据库被直接读取，也只能看到密文。
- 加密使用步骤 01 引入的字段加密密钥。密钥丢失或更换后，已加密的数据无法再还原，请自行妥善备份。
- 证据文件内容是二进制，使用同一个密钥加密后以二进制列保存；文件名等文字内容加密后以文本列保存。

## 七、五种状态

| 状态 | 代码 | 含义 | 是否算硬约束 |
|---|---|---|---|
| 待确认 | pending_confirmation | 提取器提取或用户手动补充后的初始状态，还没有经过用户确认。不参与任何建议和约束查询 | 否 |
| 生效中 | active | 用户确认后的状态。从生效日期起成为硬约束 | 是（生效日期不晚于今天时） |
| 待复核 | pending_review | 生效中的条目到了复查日或预计结束日临近。系统只负责标记，由后续的智能体在用户下次打开应用时询问。复核期间仍按原要求执行，直到用户确认解除 | 是（生效日期不晚于今天时） |
| 已解除 | resolved | 用户明确确认解除后的状态。历史记录，不再是约束 | 否 |
| 已作废 | voided | 两种情况：用户认为提取有误而作废；未确认的条目已过预计结束日期，被系统自动作废。两种情况在审计记录里以动作区分。步骤文档中的“已过期作废”即指这个状态 | 否 |

硬约束的定义：状态是生效中或待复核，并且生效日期不晚于今天。步骤 04 的约束引擎从“当前约束”的查询里读取硬约束，医嘱是权威数据，后续所有建议都要遵守。

## 八、状态流转

下表列出每个动作的起始状态、结果状态、发起方，以及是否写审计记录。所有动作都写审计记录，没有例外。

| 动作 | 起始状态 | 结果状态 | 发起方 | 审计动作 |
|---|---|---|---|---|
| 录入医嘱后提取出条目 | 无 | 待确认 | 提取器 | created |
| 手动补充条目 | 无 | 待确认 | 用户 | created |
| 修改条目 | 待确认、生效中、待复核 | 状态不变 | 用户 | edited |
| 确认生效 | 待确认 | 生效中（如果确认时已经到期，紧接着按下面的规则转为待复核） | 用户 | confirmed |
| 到期转入待复核 | 生效中 | 待复核 | 系统 | review_due |
| 过期自动作废 | 待确认 | 已作废 | 系统 | expired |
| 用户作废 | 待确认、生效中、待复核 | 已作废 | 用户 | voided |
| 继续执行 | 待复核 | 生效中 | 用户 | continued |
| 提出解除建议 | 生效中、待复核 | 状态不变，只记下建议的时间和理由 | 用户或智能体 | resolution_proposed |
| 撤回解除建议 | 生效中、待复核（且存在未处理的建议） | 状态不变，清除建议 | 用户 | resolution_proposal_cancelled |
| 确认解除 | 生效中、待复核 | 已解除 | 用户（只能是用户） | resolved |

关键约束：

- 医嘱只能由用户确认生效、只能由用户确认解除。系统和智能体只能“提出解除建议”，它不改变条目状态，也不改变当前约束；提出建议时条目必须处于生效中或待复核，对待确认、已解除、已作废的条目会返回 409，错误码 invalid_transition。确认、确认解除、作废、继续执行、修改、撤回解除建议这六个操作在代码里列为“只能由用户调用”的清单，步骤 06 不得把它们做成智能体可以调用的工具（详见《接口清单》第六节）。
- 没有建议也可以直接确认解除；有建议时，确认解除会清除建议的时间标记，保留理由。用户可以在确认解除时另填理由，填了就覆盖建议的理由。
- 已解除和已作废是终点。对它们再次修改或作废返回 409，错误码 item_closed；对它们做确认、继续执行、解除、提出解除建议等其他动作返回 409，错误码 invalid_transition；撤回解除建议返回 409，错误码 no_proposal（它们上面已经没有待处理的建议）。
- 确认生效时，饮食禁忌、饮食要求、用药相关饮食注意、运动限制这四类条目至少要有一个涉及对象，否则返回 422，错误码 subjects_required，条目保持不变。对生效中和待复核的条目做修改时同样检查，不能把它们改到没有涉及对象；待确认的条目可以自由修改。
- 修改生效中和待复核的条目时，生效日期不能改到今天之后，否则返回 422，错误码 invalid_item_dates，条目保持不变。
- 确认时，用户没有填写的预计结束日期视为长期（提取时标记的缺失字段清空）。
- 待复核的条目只能通过“继续执行”回到生效中；修改它的日期不会让它自动回到生效中。继续执行时提交新的预计结束日期和复查日期（都不填表示改为长期）；如果新的日期按今天算仍然到期，返回 422，错误码 still_due，条目保持不变，需要设置更晚的日期，或者改为确认解除。
- 作废或继续执行时，如果条目上有未处理的解除建议，建议被清除，并在审计详情里注明“建议已清除”。

## 九、到期判断与自动作废

到期判断只针对生效中的条目，满足下面任一条就转为待复核：

1. 设置了复查日期，并且复查日期不晚于今天，也就是从复查日当天起到期。原因文字：已到复查日期，请确认是否还需要继续遵守。
2. 设置了预计结束日期，并且今天已经到了“预计结束日期前 1 天”（提前天数固定为 1 天），也就是从结束日前一天起到期。按具体情况给出三种原因文字：
   - 结束日前一天：即将到预计结束日期，请确认是否还需要继续遵守。
   - 结束日当天：今天是预计结束日期，请确认是否还需要继续遵守。
   - 已过结束日：已过预计结束日期，请确认是否还需要继续遵守。

两条同时满足时，复查日期的原因优先。原因文字写入审计记录，并由系统发起，不需要用户操作。到期只是转入待复核，条目不会自动消失，也不会自动解除，待复核期间仍是硬约束。

自动作废规则：状态仍是待确认、设置了预计结束日期、并且预计结束日期早于今天的条目，被系统自动转为已作废，原因文字是“未确认的条目已过预计结束日期，自动作废”。没有设置预计结束日期的待确认条目不会被自动作废。

每次请求前刷新状态：所有医嘱接口都经过统一的入口，入口在处理请求之前先按“今天”刷新当前用户的全部条目（到期的转待复核，过期的待确认转已作废），然后才执行接口本身的逻辑。查询当前约束、查询待复核项、确认生效这三个操作还会在内部再刷新一次。因此用户看到的状态、当前约束和待复核项始终与“今天”一致，不需要后台定时任务。“今天”由服务统一提供，测试中可以固定为某一天。

## 十、当前约束与待复核项的查询规则

- 当前约束：生效中和待复核的条目，并且生效日期不晚于今天，可以按类别筛选，返回前先按上一节的规则刷新状态。返回顺序固定：先按类别，再按生效日期，再按条目在医嘱中的序号，最后按创建时间。每条带有“是否待复核”和“是否有待处理的解除建议”两个标记，并附一句提醒：以上是你确认过的医嘱约束，请遵医嘱；待复核的条目在你确认解除之前仍按原要求执行，如有疑问请咨询医生。
- 待复核项：需要用户处理的条目，即状态为待复核的，以及生效中或待复核且带有待处理解除建议的。步骤 08 的智能体在用户打开应用时读取它。
- 待确认、已解除、已作废的条目永远不出现在上述两个查询里；已解除的条目仍可以在条目列表里按状态查到，并可查看它的全部审计记录。
